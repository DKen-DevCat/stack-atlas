# prototype/live/ — ライブの試し

本物のアプリを操作しながら、その操作の流れと、画面に反映されたものを追う「ライブ」（`docs/25` §3.5、D206〜D208）が作れるかを確かめた試し。作りこむ前の確かめで、製品のコードではない。

## 動かし方

```bash
node prototype/live/run.mjs           # ブラウザの窓が開く。左のアプリを操作すると、右に流れが出る。窓を閉じると終わる
node prototype/live/run.mjs --check   # 窓を出さずに、決まった操作をして、確かめた結果を JSON で出す
```

依存は足していない。ブラウザの操作は、ビューアの e2e が使っているものを借りる（`pnpm install` 済みで、e2e 用のブラウザが入っていること）。サーバーは、手元（127.0.0.1）でだけ聞く。

## 中身

| ファイル | 役割 |
|---|---|
| `app/` | 小さなサンプルのアプリ（「本物のアプリ」の代わり）。バックエンドは無く、`sw.js` が `/api/*` の返事を差し替える。道具のための印は付けていない |
| `data.json` | サンプルのアプリの図（部品のセレクタと、挙動 3 つ）。手で書いた。本物では、エージェントがコードを読んで書く |
| `inject.js` | 道具がアプリの枠に入れるスクリプト。見るだけ（押した部品・通信・画面の変化）。何も押さない・通信を変えない |
| `viewer/` | 左の枠にアプリ、右に挙動の一覧と経路。アプリの枠からの知らせだけを受ける（出所と送り主を確かめる） |
| `run.mjs` | サーバーを 2 つ立て（アプリとビューアを別の出所にする）、ブラウザを開き、`inject.js` を入れる |

## 見せ方: 記録してから、再生する

ユーザーの指摘（2026-11-12）: 「実挙動と同じ速度だと、通信のどこがボトルネックなのか、流れはどうなのか、視覚的にわかりにくい」。実際の通信は速すぎて目で追えないので、**見せる速さを、実際の速さから切り離した**。

- 操作のあいだは記録するだけ。しばらく何も起きなくなったら、操作が済んだとみなして再生する
- 再生は、段ごと（押してから送るまで → 送ってから返るまで → … → 返ってから画面に反映されるまで）。段の長さは、実際にかかった時間に比例させるが、どんなに短い段も一定の時間は見せる
- 見せる速さ（ゆっくり・ふつう・はやい）、止める、最初から、1 段ずつ、を選べる
- 「時間の内訳」に、段ごとの実際の時間を出し、いちばん長い段の色を変える
- サンプルのバックエンドには、返事を遅らせる時間を入れた（`app/sw.js` の `LATENCY`。本物の「かかる時間」の代わり）

道具は、実際の通信を遅くしない（見るだけ）。遅い回線での動きを見たいときに通信そのものを遅らせるのは、別の機能になる。

## 分かったこと

- **アプリが一覧を丸ごと描き直すと、全部が「消えて、増えた」に見える。** 同じ中身の「消えた」と「増えた」を打ち消して、差だけを出す必要がある（`viewer/` の `net`）
- 1 回の操作のあとに、アプリが読み直しの通信も出す（投稿のあとの一覧の取得）。操作ごとに、出た順に並べて見せればよい
- 経路の 1 段目（ブラウザから出る通信まで）は実際に見え、その先（サーバーの中）は図に書かれたものを出す。見た目を分けた（実線と破線）

## まだ確かめていないこと

- 利用者の仕事の環境で使っている、返事を差し替える仕組みそのもの（ここでは、同じ形の小さなものを自分で書いた）
- 枠に入るのを拒むアプリ（応答のヘッダで拒むもの）。入らなければ、窓を 2 つ並べる
- fetch 以外の通信（フォームのふつうの送信・古い通信の仕組み・つなぎっぱなしの通信）。枠の中の包みでは見えないので、ブラウザの外から見る（8 の方法）
- ログインが要るアプリ（枠の中の Cookie）、ページを移る操作のあと
- 秘密の値を伏せる処理（この試しは、中身をそのまま出す）
- 書きこむ通信を止めて見る形（D207）
