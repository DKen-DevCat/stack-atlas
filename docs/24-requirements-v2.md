# 24. 要件 v2: 画面と挙動をたどる道具に絞る

作成: 2026-11-11。**状態: ユーザーと 1 項目ずつ確かめて確定した。この文書が要件の正。** docs/01 の R8・R9 と、docs/23 の 9-L1 以降は、この文書で置き換える。設計はまだ書いていない（§7 の未決から始める）。

## 1. 結論

- Stack Atlas は、**本物の画面を見ながら挙動を選ぶと、その経路だけが光り、データが流れる**道具に絞る。直感的にわかることを、いちばん大事にする
- **コードを読む仕事は、利用者の手元のエージェントが受け持つ**。Stack Atlas は言語を選ばず、道具の中に、特定の言語やフレームワークを前提にした処理を持たない
- 共有用の静的な全体図と、要件整理は、Claude Whiteboards に任せる

## 2. 要件

| 項目 | 内容 |
|---|---|
| 目的 | システムの全体を追える状態にする |
| Stack Atlas の役割 | 本物の画面を見ながら挙動を選ぶと、その経路だけが光り、データが流れる。直感的にわかることを、いちばん大事にする |
| whiteboard の役割 | 共有用の全体図と、要件整理 |
| 道具の性質 | Stack Atlas は言語を選ばない。道具の中に、特定の言語やフレームワークを前提にした処理を持たない |
| 埋め方 | 利用者の手元のエージェントが、コードを読んで書きこむ。どこまで読めるかは、エージェントに依る |
| Stack Atlas が持つもの | 書きこむ枠、書かれた内容の検査、画面の取りこみ、ビューア、エージェントへの手順書。手順書にも、言語ごとの手順は書かない |
| 使う順番 | まず仕事の repo で使い、そこから磨く |
| やらないこと | 言語ごとの解析。影響範囲を漏れなく保証すること |
| 前提 | 画面の取りこみは、ブラウザで開ける画面に限る |

## 3. できたと言える条件

1. 仕事の repo で、画面と挙動を選ぶと、経路が光る
2. 初めて見る人が、説明なしで追える
3. 道具のコード・設定・手順書のどこにも、特定の言語を前提にした処理が無い
4. 準備していない構成の repo に当てても、道具を変えずに同じことができる

## 4. 書き方の決まり

**要件・仕様・完成条件・手順書に、言語やフレームワークの名前を書かない。** 道具が言語に依らないのに名前が書いてあると、「その言語にだけ対応する道具だ」と読めてしまう（ユーザー、2026-11-11: 「特定の言語に依存する記述方法は誤解を産んでしまう」）。利用者の仕事の構成は「最初に使う場所の事実」で、道具の対象ではない。「まず仕事の repo で使う」「準備していない構成の repo」のように書く。

## 5. なぜ変えたか

- **全部の言語を自前で解析する道は、一人では保守できない。** 言語ごとに解析の道具を入れて版を追うことになる。しかも、画面から受け口、受け口からデータの置き場へのつながりは、言語ではなくフレームワークの書き方で決まるので、フレームワークの数だけ対応が要る（docs/23 はこの道の設計だった）
- **エージェントがコードを読んで描く道を、Claude Whiteboards（2026-11-10 公開のベータ）で試した。** 2026-11-11 に、小さな OSS のバックエンド 1 つと、フロントの画面 1 つを、エージェントが読んで板に描いた。先に書いてあった正解表と比べて、受け口 19 / 19・テーブル 7 / 7・代表の流れ 2 本がつながった。同じ repo に設定なしの Stack Atlas を当てたときは、箱 0 だった
- **whiteboard に無いもの**が、Stack Atlas の役割として残った: 本物の画面、挙動を選ぶとその経路が光る操作、図とコードの照合、800 要素を超える大きさ。ユーザーが核に選んだのは最初の 2 つ（「直感的にわかること、がいい」）
- ユーザーの言葉（2026-11-11）: 「ニッチにリッチにいきたい」「ユーザーの手元のエージェントに任せたい」「言語によって対応が変わるくらいなら持ちたくはない」「抽出機は捨てたい」

## 6. これで変わること

| 扱い | 対象 |
|---|---|
| 止める | Phase 9-L の 9-L1 以降（構文の段・型の段・レシピ。docs/23）。依存の追加（Q27）もしない |
| 捨てる | コードを読む抽出器（15 個のうち 13 個）と、それだけが使う部品・設定・テスト |
| 残す | graph の契約と検査、ビューア、画面を取りこむ部分、エージェントへの手順書（skill）、メモ・差分・配信 |
| 改める | docs/01 の R8「解析で自動生成」は「エージェントが書きこむ（人の手書きを前提にしない）」に、R9「どんなプロジェクトにも」は「道具が言語を選ばない」に読み替える |

**捨てる時期**（Claude の既定。ユーザーには 2026-11-11 に伝えた）: エージェントが書きこむ道が 1 回動いてから、1 つの PR でまとめて消す。消す前に、もう一度ユーザーに確かめる。

**失うもの**（承知のうえで決めた）:

- 毎回同じ結果が出る性質。図は毎回作り直さず、保存して差分で直す形になる
- 実リポジトリの今の結果（149 ノード / 330 エッジ）。抽出器が作ったものなので、エージェントで作り直す
- テストの大半（抽出器とその周辺のもの）
- 図の質は、エージェントの読みに左右される。だから、道具の側の検査が要になる
