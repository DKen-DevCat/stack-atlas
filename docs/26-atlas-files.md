# 26. `.stack-atlas/` に書く図の形（契約 v0）

作成: 2026-11-12。**状態: v0。10-1 の試し（エージェントに書かせて正解表と比べる）のあとで固める。** 設計は docs/25 §3.1・§3.2・§3.4、要件は docs/24。決定の番号は docs/25 の続き（D210 から）。

利用者の手元のエージェントが、コードを読んで、この形で図を書く。道具（Stack Atlas）は、書かれたものを確かめるだけで、対象のコードの意味は読まない。

## 1. ファイル

| ファイル | 持ち主 | 中身 | いま |
|---|---|---|---|
| `graph/*.yaml` | エージェント | 箱・口・項目・線 | 10-1a で読む |
| `parts.yaml` | エージェント | 画面の部品（セレクタ → 箱） | 10-1a で読む |
| `behaviors.yaml` | エージェント | 挙動（始まりと、通る線の列） | 10-1a で読む |
| `reading.yaml` | エージェント | 読んだが箱にしなかった所・読まなかった所の申告 | まだ読まない（10-1b） |
| `atlas.yaml` | 人 | repo の名前と場所、画面の URL と状態 | まだ読まない（10-1b・10-2） |
| `state/` | 道具 | 根拠の指紋 | まだ無い（10-1b） |
| `out/graph.json` | 道具 | 図を 1 つにまとめたもの（§9） | `stack-atlas bundle` が書く |

置き場は、対象が 1 つの repo ならその中、複数の repo なら、それらを束ねるディレクトリ（docs/25 Q37）。

## 2. `graph/*.yaml` — 箱と線

```yaml
nodes:
  - id: "part:comment-form"        # 箱 id。`#` は使えない
    kind: component
    name: "コメント欄 ＋ Post Comment"
    runtime: browser
    file: app/index.html            # 根拠: どのファイルの
    line: 33                        #       何行めか
    ports:
      - id: out
        dir: out
        items:
          - id: comment
            name: comment
            type: object
            children:
              - { id: body, name: body, type: string }
wires:
  - { from: "part:comment-form#out/comment", to: "endpoint:POST /api/comments#in/body.comment", via: http }
  - { from: "endpoint:POST /api/comments#out/body.comment", to: "part:comment-form#in/created", via: http, reply: true }
```

- 箱・口・項目・線・型の形と語彙は、graph.json の契約（docs/16）と同じ。項目の参照は `<箱 id>#<口>/<項目>(.<子>)*`
- 意味のまとまりごとに、ファイルを分けてよい（64 ファイルまで）。同じ箱 id を 2 度書くと誤り
- `*.v2.yaml` は、古い読みこみ（抽出器の隙間を補う道。docs/19）のファイルなので、こちらの道では読まない（D212）
- 線の根拠（呼んでいる所のファイルと行）は、10-1b で足す（docs/25 D201）

## 3. `parts.yaml` — 画面の部品

```yaml
parts:
  - id: comment-form                # 部品の id（挙動から指す）
    name: "コメント欄 ＋ Post Comment"
    box: "part:comment-form"        # この部品を表す箱
    screen: "screen:/"              # この部品が出る画面の箱（kind: screen）
    selector: "#comment-form"       # 画面の中で、この部品に当たる要素
```

対象のコードに、道具のための印は足さない。セレクタは、コードを読めば書ける。

## 4. `behaviors.yaml` — 挙動

```yaml
behaviors:
  - id: post-comment
    name: "コメントを投稿する"
    screen: "screen:/"
    trigger: { action: submit, part: comment-form }   # action: open | click | submit | input | change
    steps:
      - send: [{ from: "part:comment-form#out/comment", to: "endpoint:POST /api/comments#in/body.comment" }]
        back: [{ from: "endpoint:POST /api/comments#out/body.comment", to: "part:comment-form#in/created" }]
      - send: [{ from: "endpoint:POST /api/comments#req/row", to: "table:comments#write/row" }]
        back: [{ from: "table:comments#read/row", to: "endpoint:POST /api/comments#res/row" }]
      - send: [{ from: "part:comment-form#out/reload", to: "fn:load#in/call" }]
        say: "投稿のあと、一覧を読み直す"       # 任意の補足
    result: { say: "一覧を読み直し、コメントが 1 つ増える。", part: comment-list }
    when: { "screen:/#logged_in": true }               # 任意。キーは "<箱 id>#<分岐 id>"
```

- **挙動は線を作らない。** `graph/` にある線の上に、名前と順番を載せるだけ。線は両端の組（`from`・`to`）で名指しする
- **1 段は、送る線の列と、返る線の列。** 送る線は、1 つの箱から 1 つの箱へ。返る線は、その逆向き。1 回の呼び出しが、引数ごとに線に分かれることがあるので、どちらも列にする
- **`action: open`** は、画面を開いたときの挙動。`part` は書かない。最初の段は、画面の箱から出る
- **同時に呼ぶ所**は、段の代わりに `{ parallel: [[段, …], [段, …]] }` と書く。どの列も、分かれる前の経路から始まる
- **始まりの部品は、別の画面の部品でもよい**（その画面に、押す所が無い挙動）。変わる部品（`result.part`）も同じ（画面を移る挙動）。検査は、どちらも画面を問わない。ビューアは、部品の `screen` を見て、どの画面で光らせるかを決める（D227）

### 段のつながり（D210）

次の段は、**ここまでの経路の上の、どれかの箱から出る**。

- いちばん先の箱から出る: さらに奥を呼ぶ（例: 受け口 → データの置き場）
- 手前の箱から出る: 戻ってから、次を呼ぶ（例: 投稿のあと、同じ部品から一覧を読み直す）

経路は、始まりの箱（部品の箱。`open` なら画面の箱）から始まる。段が進むと、出る箱より先を捨てて、着く箱を足す。

設計レビューの案（docs/25 §11 高-2）は「段 n の着く箱が、段 n+1 の出る箱」だった。それだけだと、「戻ってから次を呼ぶ」が書けない。正解の図（投稿のあとの読み直し）を書いて、足りないとわかった。

## 5. check が見ること

```sh
stack-atlas check [<dir>] [--json]     # <dir>/.stack-atlas/ を検査する
```

| 検査 | 見ること |
|---|---|
| 形 | YAML として読めるか。ファイルと要素の形。箱・線・型の中身（graph.json の契約のスキーマ）。知らないキー。名前の似たファイル（`*.yml`） |
| 参照 | 箱・口・項目・線が解けるか（graph.json の検証器と同じ規則）。部品の箱があるか、部品と挙動の `screen` が画面の箱か。id の重複 |
| 挙動 | 段の線がすべて図にあるか／`send` に戻りの線が無いか／`back` が `send` の逆向きか／段がつながっているか／最初の段が始まりから出ているか／`when` のキーは、箱が宣言した分岐か／始まりと `result` の部品があるか |

どれも、契約と、図の中の参照だけを見る。対象のコードは読まない。

- **形の違う要素は、その要素だけ捨てる。** 残りの箱・線の参照の検査は、同じ回に続ける（1 つの形の誤りで、ほかの指摘が隠れない）
- **部品と挙動の中の名指しは、形を問わない**（部品の `box`・`screen`、挙動の `screen`・部品・線・分岐のキー）。解けるかどうかを「参照」「挙動」の検査が確かめ、解けなければ、何が無いかを名指しで言う。形の違う名指しで、要素を捨てない（D223）
- **指摘の場所は、id で言う**（`部品 "comment-form"`・`挙動 "post-comment" の段 2`）。id が重複しているときは、ファイルの中の何番めかも出す
- **知らないキーは誤り。** `back` を `bak` と打つと、返りの線が黙って消えるため
- **1 つの誤りで、指摘を重ねない。** 段が解けなかった・つながらなかったあとは、その挙動の残りでは、つながりを問わない。誤りを直して、もう一度 check する
- **検証器が誤りにした線は、「図にある線」として扱わない。** 行き先の無い線を通る段は、線が無いと言われる
- 終了コード: 0 = 誤りなし、1 = 図に誤りがある、2 = 検査そのものができなかった（引数の誤り・読む権限が無い、など）。`--json` では、2 のときも `{ "error": { "message", "exitCode" } }` を出す

**まだ見ないこと**（10-1b 以降）: 根拠（ファイルと行が実在し、そこに書いてあるか）、未読、古さ、部品が画面の中で見つかるか。**check が通ることは、図が正しいことではない。** 図が正しいかは、正解表と比べて確かめる（docs/25 §5）。

## 6. 上限と、読みの守り

- 読むのは、決まった名前のファイルだけ（`graph/*.yaml`・`parts.yaml`・`behaviors.yaml`。`*.yml` は読まずに、名指しで誤りにする）。シンボリックリンクは辿らない。1 ファイル 1MB まで。YAML の別名の展開は 100 まで（今の補いのファイルと同じ守り。`packages/core/src/local-files.ts`）
- 文字列・数・`true` / `false`・配列・`{ キー: 値 }` のほかの値（日付・集合・無限大など。YAML は作れる）のあるファイルは読まない。まとめた graph.json が、契約と違う形になるため
- 箱 2000・線 5000・部品 2000・挙動 500・1 つの挙動の段 64 まで

## 8. エージェントに書かせる試し（10-1c）

手順書（`harness/guide/GUIDE.md`）だけを渡したエージェントが、この形で図を書けるかを確かめる。対象は、ライブの試しのサンプルのアプリ（`prototype/live/app`。2 ファイル）。対象を repo の外に写し、手順書と例を隣に置いて、新しいエージェント 1 体に「手順書に従って図を書く」とだけ頼む。正解の図（`packages/core/src/__tests__/fixtures/atlas-live/`）と、この文書は見せない。

### 8.1 正解表（結果を見る前に書いた。2026-11-12）

| 見るもの | 正解 |
|---|---|
| 画面 | 1 つ（`/`） |
| 受け口 | 3 つ: `GET /api/comments`・`POST /api/comments`・`DELETE /api/comments/{id}` |
| データの置き場 | 1 つ（コメント） |
| 操作を受ける部品 | 2 つ: コメントを書く欄（送信）、コメントの削除のボタン（押す。行ごとに出る） |
| 変わる部品 | コメントの一覧 |
| 挙動 | 3 本: 開く・投稿する・削除する |
| 開く | 一覧を読む通信 → 置き場を読む → 一覧に出る |
| 投稿する | 送るものは `comment: { body }` → 置き場に 1 行書く → 返るものは `comment` → **一覧を読み直す**通信 → 一覧に出る |
| 削除する | 送るものはパスの中の `id` → 置き場から 1 行消す → 返るものは無い（204）→ **一覧を読み直す**通信 → 一覧に出る |
| 細かい所（書けていれば加点） | 削除のボタンは、自分の書いたコメントにだけ出る（条件）。件数の表示も変わる |

採点: 受け口・置き場・部品・挙動が正解と同じ数だけあるか。挙動ごとに、送るもの・メソッドとパス・読み書きする置き場・読み直しが合っているか。正解に無い箱や線（作り話）が無いか。検査がエラー 0・警告 0 か。

| 検査 | エラー 0・警告 0 | エラー 0・警告 0（箱 11・線 17・部品 4・挙動 3） | 合っている |
| 画面 | 1 | 1 | 合っている |
| 受け口 | 3 | 3（メソッドとパスも同じ） | 合っている |
| データの置き場 | 1 | 1 | 合っている |
| 操作を受ける部品 | 2 | 2（セレクタは、コードの要素と合っている） | 合っている |
| 変わる部品 | 一覧 | 一覧と、件数の行 | 合っている（正解より細かい） |
| 挙動 | 3 本 | 3 本（開く・投稿する・削除する） | 合っている |
| 送るもの・返るもの | 表のとおり | 同じ | 合っている |

正解の図（箱 9・線 15）との違いは、箱の分け方だけ: 画面に描く処理と、件数の行を、箱にしている。どちらも、コードに実際にある。

**限界**: 対象は 2 ファイルの小さなアプリ。エージェントは 1 体・1 回。正解の図と、設計の文書を読まないように頼んだだけで、読めないようにはしていない（本人の報告では、対象の外は読んでいない）。大きな repo、複数の repo、通信が画面の側とサーバーの側に分かれる作りでは、まだ試していない。

### 8.4 試しで決めたこと・わかったこと

| # | 決定 | 理由 |
|---|---|---|
| D217 | データの置き場で消すときは、`key`（どれを）と、`write` の `remove`（何も運ばない項目）へ線を引く | エージェントが、決まりの無い所で、この形を選んだ。読んで意味が通る |
| D218 | 契約 v0 の形は、このまま進める（固めるのは、図をライブの入力に流してから） | 手順書だけで、検査を通り、正解表と合う図が書けた。形そのものへの指摘は無く、指摘は手順書の説明の不足だった |

わかったこと:

- **検査は、今回は 1 度も働かなかった。** エージェントは、最初から形の合った図を書いた。検査の値打ちは、もっと大きな図や、直しを重ねる場面で確かめる
- **1 つの段に、送る線が 2 本**（どれを・消す）という書き方が、自然に出た。契約はこれを許している
- **変わる部品を 1 つしか書けない**（`result.part`）ことに、エージェントは気づいて報告した。ライブでは、画面の変わった所を実際に見るので、いまは 1 つのままにする

## 9. まとめる（bundle）と、契約への組みこみ（10-1c の後半。2026-11-12）

```sh
stack-atlas bundle [<dir>] [-o <outDir>] [--json]   # <dir>/.stack-atlas/ を検査して、<outDir>/graph.json にまとめる
stack-atlas serve <outDir>                          # 今のビューア（配線図）で開く
```

- 既定の出力先は `<dir>/.stack-atlas/out`。図に誤りがあれば、書かずに終了コード 1。出力先や、その途中がシンボリックリンクなら、書かずに終了コード 2
- 図に誤りがあって書かなかったとき、前に bundle が書いた `graph.json` が出力先に残っていれば、消す（古い図を、今の図としてビューアに出さない。D225）。bundle が書いたとわからない `graph.json`（`project.generator.v2` が `"atlas"` でないもの・読めないもの・リンク）には触らず、残っていると知らせる。`--json` では `removed`・`kept` に出す
- 出力先に `index.html` があれば、`serve` が同梱のビューアではなく、それを配信することを知らせる（`--json` では `notes`）。`serve` は、シンボリックリンクの先が出力先の外なら配信しない（D226。docs/11）
- まとめた `graph.json` は、契約 v2 に、任意の `parts`（部品）と `behaviors`（挙動）を足したもの（docs/16 §8.3）。`project.generator.v2` は `"atlas"`
- **エージェントが書いた図を、手を入れずにまとめて、今のビューアで開けた**（箱 11 が、ブラウザ・サーバー・データの 3 列に並ぶ）。「くわしく見る」先の配線図は、作り直さなくても使える

| 場所 | 中身 |
|---|---|
| `packages/schema/graph-v2.schema.json`・`src/v2.ts` | `parts`・`behaviors` の形（スキーマが正。型とのずれは `v2.test.ts` が見る） |
| `packages/schema/src/behaviors.ts` | 部品と挙動の検査（`checkBehaviors`）。`validateGraphV2` から呼ぶ。段のたどり方（`walkBehavior`）と、経路の進め方（`advancePath`）も、ここに置く |
| `packages/core/src/atlas/check.ts` | 検証器の指摘の場所（`/behaviors/1/steps/2` など）を、「どのファイルの、どの挙動の段か」に直す |
| `packages/core/src/atlas/bundle.ts`・`packages/cli/src/commands/bundle.ts` | まとめる |
| `packages/wiring/src/behavior-view.ts` | 挙動を、見せるための段の列にする（`behaviorView`）。段ごとに、どの箱からどの箱へ、何を送り、何が返るか。画面の側から受け口へ出る通信の段には、メソッドとパスが付く（ライブが、実際の通信と照らす段） |

| # | 決定 | 理由 |
|---|---|---|
| D219 | 部品と挙動の検査の決まりは、契約の検証器（`@stack-atlas/schema`）に 1 つだけ置く。図を書く側（core）は、指摘の場所を人が読む形に直すだけ | ビューアが graph.json を読むときも、同じ決まりで確かめる。決まりを 2 か所に書かない |
| D220 | まとめたものは、新しい形式にせず、graph.json v2 に `parts`・`behaviors` を足す | 今のビューア・検証・差分が、そのまま使える。配線図（くわしく見る先）を作り直さない |
| D221 | 挙動の見せ方（段の列・深さ・送るもの・返るもの・通信の段）は、`@stack-atlas/wiring` に置く | ビューアは core に依存しない（D44）。見せ方の決まりを、ビューアの外で試せる |
| D222 | 形の検査は、部品と挙動も 1 つずつ契約のスキーマに掛ける | 1 つの挙動の形の誤りで、ほかの全部の検査が飛ばないようにする（D214 と同じ理由） |
| D223 | 部品と挙動の中の名指し（箱・部品・線・分岐のキー）の形は、契約のスキーマでは問わない。解けるかどうかを、検証器が確かめる。部品と挙動の `id` の形（`#` と制御文字を使わない）は、今までどおりスキーマが確かめる | 形の違う名指しは、必ず解けないので、検証器が拾える。スキーマで断ると、要素ごと捨てられ、指摘が「パターンに合わない」という読みにくい文になり、その要素を指すほかの要素に偽の指摘が出る（レビュー 1） |
| D224 | 段のたどり方（並んだ列の扱い）と、経路の進め方（D210）は、検査と、見せる形（`behaviorView`）が、同じ関数（`walkBehavior`・`advancePath`）を使う | 決まりを 2 か所に書くと、検査が通した挙動を、ビューアが違う深さで描くことが起こる（レビュー 8） |
| D225 | bundle が、図の誤りで書かなかったとき、前に bundle が書いた graph.json を消す。bundle が書いたとわからないものには触らない | 残すと、`serve` が古い図を出し続ける。消す相手を印で確かめるのは、同じ出力先に、ほかの手段で作った graph.json があることがあるため（レビュー 7） |
| D226 | `serve` は、シンボリックリンクを解いた先が、配信する場所（出力先・ビューア）の外なら配信しない。中を指すリンクは、今までどおり配信する | 既定の出力先は、対象の repo の中。repo に仕込まれたリンクの先（repo の外のファイル）を、配信していた（セキュリティのレビューの注意 1）。中を指すリンクを配信することは、前のレビュー（8-3b）のテストが決めている |
| D227 | 始まりの部品も、変わる部品も、別の画面の部品でよい。検査は、部品の画面と、挙動の画面が同じかを問わない | §4 の決まり（その画面に押す所が無い挙動）。画面を移る挙動では、変わる部品が移った先の画面にある（レビュー 2 は、この決まりと食い違うので直さない） |
