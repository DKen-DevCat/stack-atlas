# 25. 設計: 画面から始める。コードはエージェントが読む（Phase 10）

作成: 2026-11-11。**状態: ユーザーの確認（§7）、入口のモック（§3.5）への反応、設計レビュー（1 回。§11）を反映した版。次は 10-1。** ライブ（D206〜D208）は、設計レビューのあとに足した（このときは、レビューを受けていない。10-2 で作りこむ前に、設計を docs/27 に書き、安全の面を見直して、レビューを 1 回受けた）。 要件は docs/24。決定の番号は **D190 から**、質問の番号は **Q34 から**。

この文書も docs/24 §4 の決まりに従い、言語やフレームワークの名前を書かない（今あるコードの部品の名前を指すときを除く）。

## 0. なぜ書くか

- 要件 v2（docs/24）で、Stack Atlas の役割は「本物の画面を見ながら挙動を選ぶと、その経路だけが光り、データが流れる」に絞られた。コードを読むのは利用者の手元のエージェントで、道具は言語に依る処理を持たない
- 今のビューアを、フィクスチャ（71 箱・143 本、画面 3 つ）で見直した（2026-11-11）。配線図の面で名前付きの始点を 1 つ選ぶと、**線のほとんどが光り、経路が 1 本に見えない**。画面は、たくさんある箱の 1 つとして小さく出る。口と項目が全部見えていて、字が細かい。技術者が調べるための図としては正しいが、「直感的にわかる」入口ではない
- 一方で、材料はほとんど揃っている: 箱・口・項目・線の契約（docs/16）、エージェントが箱を書くファイルの形（docs/19 §3）、画面を取りこんで安全に描く仕組み（docs/18 §3.3）、たどる規則と球（`packages/wiring`）、検査（`--strict`）

## 1. 結論

- **入力は 1 つの形にする。** エージェントが、対象の repo の中の `.stack-atlas/` に、箱と線と挙動を書く。今ある「手書きの部分グラフ」（docs/19 §3）を、唯一の入力に格上げする。抽出器・合流・補い（overrides の `v2:`）は無くす（D190）
- **挙動を、名前のある 1 本の経路として持つ。** 今の「名前付きの始点」は、始点からたどれるもの全部を光らせる。挙動は「どの画面の、どの部品を、どうすると」「どの線を順に通って」「何が返り、画面がどう変わるか」を、段の列として書く（D191）
- **ビューアの入口を画面にする。** 本物の画面を大きく出し、その上の部品か、挙動の一覧から 1 つ選ぶ。選んだ挙動の経路だけを、左から右への 1 本の帯で出し、球を流し、段ごとに送るものと返るものを出す。今の配線図は「くわしく見る」先に回す（D192）
- **検査は、言語を知らずにできることだけをする。** 形、参照、根拠（ファイルと行が実在し、名前がそこに書いてあるか）、未読（どの箱にも出てこないファイル）、古さ（根拠の行が、書いたあとで変わったか）（D193）
- **画面の取りこみは「ブラウザで開いたものを保存する」の 1 通りにする。** 部品は、エージェントがセレクタで指し、道具が写しの中で測る。対象のコードに印を足させない（D194・D203）

```
今
  コード ─▶ 抽出器 15 個 ─▶ 合流・補い ─▶ graph.json ─▶ ビューア（3D の地図 ｜ 配線図）
            （言語ごと）                                  画面は箱の 1 つ。始点を選ぶと全部光る

これから
  コード ─▶ 利用者の手元のエージェント ─▶ .stack-atlas/（箱・線・挙動・画面の設定）
            （手順書に従って読んで書く）        │
                                               ├─▶ check（形・参照・根拠・未読・古さ）─▶ 直す所の一覧 ─▶ エージェントへ戻る
  動いている画面 ─▶ capture（ブラウザで保存・部品を測る）─┤
                                               └─▶ bundle ─▶ ビューア（画面 → 挙動 → 経路の帯 ─▶ くわしく: 配線図）
```

## 2. 全体像: 誰が何を受け持つか

| 担当 | 受け持つもの | 言語に依るか |
|---|---|---|
| 利用者の手元のエージェント | コードを読む。箱・線・挙動・部品のセレクタを書く。check の指摘を直す | 依る（ここだけ） |
| 人 | 対象のアプリを起動して URL を渡す。挙動の名前と文を直す。エージェントに読ませてよいかを決める | — |
| Stack Atlas | 書く形（契約）、check、capture、bundle、ビューア、手順書 | 依らない |

## 3. 構造

### 3.1 書く形（`.stack-atlas/`）

| ファイル | 持ち主 | 中身 | 今あるもの |
|---|---|---|---|
| `atlas.yaml` | 人 | repo の名前と場所の表、画面ごとの URL、画面の状態とその準備（§3.3）。エージェントは書かない | 設定のうち、人が決めることだけを残す |
| `graph/*.yaml` | エージェント | 箱・口・項目・線 | 「手書きの部分グラフ」。今は、抽出器の箱へつなぐ線だけ補いの側に書く決まりがある。抽出器が無くなるので、線はすべてここに書く |
| `behaviors.yaml` | エージェント | 挙動（§3.2） | `views.yaml` と v1 の `flows.yaml` を 1 つにする |
| `parts.yaml` | エージェント | 画面の部品のセレクタ（§3.3） | `regions.yaml` の置き換え（座標ではなくセレクタ） |
| `reading.yaml` | エージェント | 読んだが箱にしなかったファイルと、読まなかった所の申告。理由が必須（§3.4） | 抽出器の「読んだ」の申告の置き換え |
| `DECISIONS.md` | エージェント | 推定したこと | そのまま |
| `state/` | 道具 | 根拠の指紋（§3.4）と capture の記録。人もエージェントも手では書かない | 今の「道具の出力は手で書かない」の決まりを引き継ぐ |

- **人の持ち物とエージェントの持ち物を、ファイルで分ける。** URL と状態の準備は人のファイルにだけ書く。エージェントが書くファイルに URL を入れない（§3.3 の守りが、ファイルの単位で効く）
- **置き場**: `.stack-atlas/` は、対象が 1 つの repo ならその中に、複数の repo なら、それらを束ねる 1 つのディレクトリに置く（§7 の Q37）。箱の根拠は `<repo の名前>/<repo からの相対パス>` で書く。repo の名前と場所は `atlas.yaml` の表で決める。根拠・未読・古さは、repo ごとに数える
- 箱には根拠（`file` と、始まりと終わりの行）を書く。**線にも根拠を書く**（呼んでいる所のファイルと行。§3.4）。コードに無い箱（利用者・外のサービスなど）は、根拠が無い理由を `meta` に書く
- 深さはエージェントが決める。**挙動の経路の上は項目まで、それ以外は箱まで**を手順書の目安にする。箱までの粗い箱の書き方と、今の検証が出す「口の単位」の警告の扱いは、10-1 で決める
- 今の設定ファイル（`stack-atlas.config.yaml`）と補い（`stack-atlas.overrides.yaml`）は無くす。抽出器に何をどこから読むかを伝えるためのものだったので、役目が無くなる。人が決めること（repo の場所・URL・状態）だけが `atlas.yaml` に残る
- **契約に足すもの**: 挙動、画面の状態、線の根拠、根拠の行の範囲。箱・口・項目・線の形は docs/16 のままだが、「契約は変えない」ではない

### 3.2 挙動

```yaml
# .stack-atlas/behaviors.yaml（形の例。名前は架空）
- id: post-comment
  name: "コメントを投稿する"
  screen: "screen:/article"            # 画面の箱
  trigger: { part: "part:comment-form", action: submit }   # 画面の部品と、操作
  steps:                                # 段を、順に。段は「送る線の列」と「返る線の列」
    - send: [{ from: "part:comment-form#out/body", to: "handler:create-comment#in/body" }]
      back: [{ from: "handler:create-comment#out/done", to: "part:comment-form#in/done" }]
      say: "入力した本文を送る"         # 任意の補足
    - send: [{ from: "handler:create-comment#out/call_1.body", to: "endpoint:POST /comments#in/body" }]
      back: [{ from: "endpoint:POST /comments#out/body", to: "handler:create-comment#in/ret_1" }]
    - send: [{ from: "endpoint:POST /comments#req/body", to: "store:comments#write/row" }]
  result: { say: "一覧を読み直し、コメントが 1 つ増える", part: "part:comment-list" }
  when: { "screen:/article#logged_in": true }   # 分岐（任意）
```

- 線は、今の名前付きの始点と同じく `{ from, to }` で名指しする（線に id は無い。両端の組で一意）。1 回の呼び出しは、引数ごとに線が分かれることがあるので、送る・返るはどちらも列にする
- `steps` の線は、`graph/` にある線でなければならない。挙動は線を作らない。線の上に名前と順番を載せるだけ
- check が確かめること: 段の線がすべて `graph/` にある／段がつながっている（次の段は、ここまでの経路の上の、どれかの箱から出る。docs/26 §4、D210）／始まりの部品が、最初の段の出る箱である／`when` のキーは、箱が宣言した分岐だけ
- ファイルの形と、check が見ることの細かい決まりは **docs/26**（契約 v0。10-1a で実装した）
- 画面を開いたときの読みこみも、挙動の 1 つとして書く（`action: open`）
- ビューアは `steps` に載った箱・線・項目だけを光らせる。今の「始点からたどる」は、配線図の側の操作として残す

モック（§3.5）で要るとわかったもの:

| 要るもの | 書き方 |
|---|---|
| 行きと戻り | 段は、送る線の列（`send`）と返る線の列（`back`）。今の契約は、往復の相手を箱の単位でしか持たないので、組は挙動の側で名指しする。送るもの・返るものの表示は、線の項目から作る |
| 同時に呼ぶ（経路が分かれる） | 段の列の途中に、並んだ列を書ける（`parallel: [[…], […]]`）。ビューアは横に並べる |
| 条件で変わる（同じ操作で、送り先が変わる） | 挙動に分岐（契約の variants）を付け、段に `when` を書く。ビューアは切り替えを出す |
| 始まりの部品が、この画面に無い | `trigger.part` が別の画面の部品でもよい。その画面の一覧では「ほかの画面から」と出す |
| 見ている人で、部品が出たり消えたりする | 画面の状態（§3.3）ごとに取りこむ。挙動は、始まりの部品が出る状態を `when` に書く |
| 結果 | 文と、変わる部品（任意）。取りこんだ画面は写しなので、押しても中身は変わらない（§3.5） |

箱の種類と段の数は、挙動ごとに違ってよい。モックの「部品 → サーバーの処理 → 受け口 → リポジトリ → データの置き場」は、その例の repo の形で、道具が決める並びではない。

### 3.3 画面の取りこみ

- `stack-atlas capture`: `atlas.yaml` の URL をブラウザで開き、描かれた結果の HTML と CSS を、**ページ全体の高さで**保存する。保存したものは、今の消毒（許可リスト。docs/18 §3.3）を通してから置く
- **部品の測り方**: capture は、`parts.yaml` のセレクタに当たった要素に、**保存する写しの側で**道具の印を付ける。位置は、今と同じくビューアが写しの中で測る（今は対象のコードが付けた印を測っている。測る相手を道具の印に替える）。check の「測れたか」も、写しに印があるかで判定する。動いている画面で測った座標は使わない（写しとずれるため）
- **押す所はビューアの側で受ける。** 写しを入れる枠は、今と同じく押せないままにする（写しの中のリンクやボタンを動かさない）。部品の枠と当たり判定は、ビューアが写しの上に描く
- **入力欄などを写しに残す。** 今の消毒は、入力欄や一部の図形の要素を丸ごと落とす。挙動の始まりが入力欄のこともあるので、動かない見た目だけの形で残す
- **capture 用に、消毒を足す。** ログインした画面には、送信用のトークンや利用者の id が残りうる。`meta` は表示に要るものだけ残す。隠した入力欄と、入力欄の値を落とす。`data-*` は道具の印だけ残す。資産（画像・CSS・フォント）は、人が渡した URL と同じ出所のものだけを取り、大きさと種類に上限を置く。保存先は、既定で版の管理から外す
- 起動と URL は人が用意する。エージェントは URL を足さない・変えない（今の手順書の決まりを引き継ぐ。実サイトや repo の外へ接続させないため）。capture は、既定では手元のホストだけに接続する。それ以外は、人が `atlas.yaml` で名指ししたホストだけ。**capture を、エージェントに許すコマンドに入れない**
- **capture は、画面を開くだけで、何も押さない。開いている間、書きこむ通信はいつも止める**（開いただけで何かを送る画面があっても、環境を汚さない。D207）
- 1 つの画面を、**状態ごとに**取りこめる（例: ログインしているとき・していないとき）。状態の名前と、その状態で開くための準備（ログイン済みの状態のファイルなど）は、人が `atlas.yaml` に書く。状態は、箱が宣言した分岐の値の組に結ぶ（例: 状態「著者」＝ `logged_in: true`・`is_author: true`）。今の契約は画面を 1 組しか持てないので、**状態ごとの写しを契約に足す**。ビューアは状態の切り替えを出し、挙動の始まりの部品が出ない状態では、その挙動を「この状態では押せない」と出す
- 対象のコードに印（今の `data-component`）を足させない。セレクタは、エージェントがコードを読めば書ける
- 特定のビルドの成果物の置き場を読む設定（今の `from: next-export`）は無くす。静的な HTML の置き場を直接指す形だけ残す

### 3.4 check

| 検査 | 何を見るか | 言語を知らずにできる理由 |
|---|---|---|
| 形・参照 | schema、箱・口・項目・線・挙動の段が解けるか | 契約だけを見る |
| 根拠 | 箱と線の `file` が repo にあるか。申告した行の範囲に、申告した文字列が書いてあるか | 文字列の一致だけを見る |
| 未読 | git が追跡するファイルのうち、どの箱・線の根拠にも、`reading.yaml` の申告にも出てこないもの | パスだけを見る |
| 古さ | 根拠の行の範囲の中身が、受け入れたときの指紋と変わっていないか | ハッシュだけを見る |
| 挙動 | §3.2 の 4 つ。capture の記録があるときは、始まりの部品が写しの中で測れたか | 契約と capture の記録だけを見る |

- **根拠の検査が言えるのは「その場所を見た」まで。** 線の意味が正しいことは言えない。申告する文字列には下限を置く（短すぎる字句や、記号だけの字句は受け付けない）。表示用の名前はコードに無いことが多いので、名前とは別に「そこに書いてある文字列」を申告させる
- **指紋は、道具が、道具の持ち物（`state/`）に書く。** `check --accept` が、いまの根拠を受け入れて指紋を記録する。エージェントが書くファイルには入れない
- **行の番号に結ばない。** 上に 1 行足しただけで、同じファイルの箱が全部「古い」にならないようにする。中身で探し直して、行の番号のずれは直す。空白だけの違いは無視する。範囲の外が変わったときのために、ファイル全体の指紋を粗い 2 段目（「要確認」）として持つ
- 「古さ」が、失った「毎回同じ結果」の代わりになる。図は作り直さず、**check が出した「変わった箱と線」だけを、エージェントが読み直して直す**
- **未読は関門にしない。** 今の報告（9-L0）が持つ言語の表と、置き場の名前の表は消す（docs/24 §3 の条件 3）。表が無いと、テストや文書や画像も未読に出るので、エラーにはせず、最上位のディレクトリごとの数と割合で出す。除外は、対象の repo 自身の無視の設定と、`reading.yaml` の申告から取る。申告は理由が必須で、全部を指す書き方は受け付けない
- **check を 2 段に分ける。** capture の記録が無くても通る段（形・参照・根拠・未読・古さ・挙動の 4 つ）と、記録があるときの段（部品が測れたか）。エージェントは capture を回せないので、前の段だけで自分の仕事を閉じられるようにする
- check が根拠のファイルを読むときも、今の読みの守り（repo の中に閉じる・リンクを辿らない・大きさの上限）を通す。秘密らしいファイルの中身を、出力に写さない
- check の出力は、人が読む形と、エージェントが読む JSON の 2 つ（今の `--dry-run --json` を引き継ぐ）

### 3.5 ビューア

モックで確かめた形（2026-11-11。2 版でユーザーが「めちゃくちゃいい感じ、わかりやすい」）:

```
 画面 [ /article ▾ ]   状態 [ 著者 | ほかの利用者 | ログインなし ]   □ 部品の枠
┌─────────────────────────────────┬──────────────────────────────┐
│ 本物の画面                        │ この画面の挙動                  │
│  ┌───────────────────────────┐  │ (ページを開く)(コメントを投稿する)… │
│  │ …            [ Delete ]   │  │ ───────────────────────────  │
│  │ ┌ コメント欄 ───────────┐  │  │ コメントを投稿する   条件: …      │
│  │ │        [ Post Comment ]│ │  │ ┌ 画面の部品 ──────────────┐  │
│  │ └───────────────────────┘ │  │ └───────────────────────┘  │
│  │   ↑ 挙動の始まりの部品に枠   │  │   ↓ 送るもの   ↑ 返るもの       │
│  └───────────────────────────┘  │ ┌ 次の箱 ─────────────────┐  │
│                                 │ └───────────────────────┘  │
│                                 │   …（上から下へ）              │
│                                 │ 結果: コメントが 1 つ増える      │
└─────────────────────────────────┴──────────────────────────────┘
```

- **画面と経路を横に並べる。画面に何も重ねない・貼りつけない**（D197）。1 版は、経路の帯を画面の下に貼りつけて画面に重ね、ユーザーに「画面構成がナンセンス。挙動の確認がしにくい」と差し戻された
- 左が画面、右が「この画面の挙動」の一覧と、選んだ挙動の経路。経路は上から下へ。箱と箱の間に、送るもの（行き）と返るもの（戻り）を出す。箱の下に、根拠のファイルと行を出す
- 画面の上の部品を押しても、挙動の一覧から選んでも、同じ挙動が選ばれる。球は、行きを下へ、戻りを上へ流れる
- 同時に呼ぶ所は、経路を横に 2 列に分ける。条件で送り先が変わる所は、切り替えを出す
- 「くわしく見る」は、今の配線図を、その挙動の箱と線だけを光らせた状態で開く（モックには入れていない）

モックのファイルは `prototype/entrance-mock.html`（ユーザーの了承を得て入れた。箱の下のファイル名と行は、試しに読んだ小さな OSS のもの）。

**モックと本物の違い**（D198）: モックは、部品を押すと画面の中身が実際に変わる（コメントが増える）。本物の画面は取りこんだ写しなので、押しても中身は変わらない。写しの入口では、結果の文を出し、変わる部品を光らせる。実際の挙動は、次のライブで見せる。

#### ライブ: 本物のアプリを動かしながら見る（D206）

ユーザーの要望（2026-11-11）: 「できれば実挙動を見たい」「ここでこんな流れで、画面に反映されました、って、流れと状態を追いたい」。**ライブを、写しを使う入口より先に作る**（D208）。

1 回の操作について、次の順に見せる: 押した部品 → 光る経路 → 実際に送った中身 → 実際に返った中身 → 画面のどこが変わったか（変わる前と、変わったあと）。

並びは、モックと同じにする見込み: 左の枠に本物のアプリ、右に挙動の一覧と経路。本物のアプリを枠に入れられない場合は、窓を 2 つ並べる。

- 道具がブラウザの窓を 1 つ開き、**人が**その窓で本物のアプリを操作する。道具は 2 つのことだけを見る: 押された要素が `parts.yaml` のどの部品か、そのあとブラウザから出た通信（メソッド・パス・応答の状態）は何か
- ビューアは、その部品から始まる挙動の経路を、その場で光らせる。実際に出た通信を、経路の最初の段に並べて出す
- **道具は押さない。** 操作するのは人だけで、道具は見るだけ。エージェントが書いたセレクタを使って、道具が何かを押すことはない
- **実測できるのは、ブラウザから出る通信まで。** その先（受け口からデータの置き場まで）は、図に書かれた経路を光らせる。実測した段と、図に書かれただけの段を、表示で分ける
- 副産物として、**図の最初の段と、実際の通信が合っているか**を、道具が比べられる。言語を知らずにできる照合で、食い違いは check の指摘と同じ扱いで出す
- 通信の中身には、秘密が入りうる。既定では値を出さず、キーの名前だけを出す。保存しない
- **環境を汚さない**（D207。ユーザー、2026-11-11: 「これは動作確認の立ち位置なので、環境汚染はよろしくない。手元の開発環境に書きこむのはよい」）:
  - ライブは、**手元で起動した環境だけ**につなぐ。共有の開発用・検証用の環境には、ライブではつながない（名指しでつなぐ抜け道も作らない）
  - **「止めて見る」**を持つ: 書きこむ通信を、ブラウザから出る直前で止めて、送ろうとした中身だけを見せる。どこにも書かれない。画面は変わらない（アプリからは失敗に見える）。手元でも汚したくないときに使う
  - 返事を差し替える仕組みを使う環境では、通信はブラウザの中で受け取られるので、もともとどこにも書かれない
- 接続先の URL は人が渡す。手元で通した場合、消す操作は手元のデータを本当に消す
- **道具は、アプリの動きを作らない。** 投稿が画面に反映されるのは、本物のアプリが、つながっている先（手元のバックエンド・開発用の環境・返事を差し替える仕組み）に実際に送るから。つながる先が無ければ、アプリの失敗がそのまま見える。道具は、それをごまかさない
- 要るのは、**手元で動く環境**が 1 つ（D207）。フロントとバックエンドを手元で起動したものでも、フロントだけ起動して、返事を差し替える仕組みを使うものでもよい。本番にも、共有の環境にもつながない。利用者の仕事の環境は、どちらもできる（2026-11-11）。差し替える仕組みが通信を途中で受け取る形でも、道具から通信が見えるかは、10-2 の試しで確かめる
- 写しの入口は残す。アプリを起動していない人が見るとき・共有・CI のために要る

**試しの結果**（2026-11-11。`prototype/live/`。小さなサンプルのアプリと、返事を差し替える小さな仕組みで確かめた）:

| 確かめたこと | 結果 |
|---|---|
| 本物のアプリを、ビューアの左の枠に入れて動かせる（別の出所の枠） | できた |
| 押した・送信した要素が、図のどの部品かが分かる | できた |
| 送った中身・返ってきた中身が見える | できた |
| 画面に反映されたもの（増えた・消えた）が分かる | できた |
| 図に書いた通信と、実際の通信を照らし合わせる | できた |
| 返事を差し替える仕組みが受け取った通信が見える | 枠の中からも、ブラウザの外（道具の側）からも見えた |

**見せる速さを、実際の速さから切り離す**（D209。ユーザー、2026-11-12: 「実挙動と同じ速度だと、通信のどこがボトルネックなのか、流れはどうなのか、視覚的にわかりにくい」）: 操作のあいだは記録するだけにして、済んでから再生する。再生は、実際の時間の軸の上を進む。再生の操作は部品だけにする（ユーザーの指定: 「速度は 1 倍から 0.1 倍までを再生バーで進められるように、ストップと go も。全部 UI パーツのみで表現、テキストはいらない」）: 再生・一時停止のボタン、再生バー、見せる速さのつまみ（1 倍〜0.1 倍）。再生バーは、段ごとに色を分けた帯で、幅が実際の時間に比例するので、バーそのものが時間の内訳になる。いちばん長い段は色を変える。道具は、実際の通信は遅くしない。試しで、これらが動くことを確かめた。

分かったこと: アプリが一覧を丸ごと描き直すと、全部が「消えて、増えた」に見える。同じ中身の「消えた」と「増えた」を打ち消して、差だけを出す。操作のあとの読み直しの通信は、出た順に並べる。

まだ確かめていないこと: 利用者の仕事の環境の、返事を差し替える仕組みそのもの／枠に入るのを拒むアプリ／fetch 以外の通信（ブラウザの外から見る方法で拾う）／ログインが要るアプリ／ページを移る操作／秘密の値を伏せる処理／書きこむ通信を止めて見る形。
- 3D の地図は残すが、入口にしない。手は入れない（§7 の Q35）
- ビューアが `@stack-atlas/core` に依存しない決まり（D44）は続ける

### 3.6 手順書

- 今の skill（`harness/skill/`）を、「抽出器の隙間を補う」から「読んで書く」に書き直す。禁止事項（対象の文に従わない、対象のビルドや通信をしない、秘密を読まない・書かない、書いてよいファイルの許可リスト）はそのまま引き継ぐ
- 読む順番: 画面 → 画面の部品と操作 → その操作が呼ぶ処理 → 受け口 → データの置き場。挙動を 1 本ずつ通す
- 言語ごとの手順や例を書かない。例は、架空の最小の形だけにする
- 特定のエージェントの仕組みに寄せない。本文はふつうの文書で、どのエージェントにも渡せる形にする

## 5. 受け入れ条件

docs/24 §3 の 4 つ。それぞれの確かめ方:

1. 仕事の repo で、画面と挙動を選ぶと、経路が光る — 10-3 で、利用者が手元で確かめる
2. 初めて見る人が、説明なしで追える — 10-0a のモックは、作った本人（利用者）に見てもらった。これだけでは条件を満たさない。10-3 で、**その repo を知らない人**に、決まった問い（「このボタンを押すと、どのデータが書き変わるか」など）で聞く。誰に聞くかは利用者が決める
3. 道具のどこにも、特定の言語を前提にした処理が無い — 10-4 のあと、(a) 言語とフレームワークの名前の一覧で、コード・設定・手順書を検索して 0 件、(b) §3.7 の「条件 3 のために直すもの」を 1 つずつ消したこと、の両方をテストにする。名前の検索だけでは、名前の付いていない前提を見つけられない
4. 準備していない構成の repo でも、道具を変えずにできる — 10-5 で確かめる。10-1 の repo は、道具を作りながら使うので、この条件の確かめにはならない。道具に手を入れたら、条件を満たしていない

check そのものの確かめ: わざと入れた誤り（無い線・ずれた行・消えたファイル・つながらない段）を、check が見つけることをテストにする。check が通ることは、図が正しいことではないので、10-1 では正解表と比べる。

## 9. 採らなかった案

- **抽出器を「正確な下書き」として残す**: 言語によって道具の振る舞いが変わる。ユーザーが退けた（2026-11-11）
- **MCP を最初から作る**: 正がファイルにある以上、同じ操作の入口が 2 つになる。要るとわかってから足せる
- **whiteboard の上に全部を載せる**: 本物の画面を載せられず、選んだ挙動だけを光らせる操作が無い（docs/24 §5）
- **今の配線図を磨いて入口にする**: 口と項目を全部見せる図は、どう磨いても最初の 1 枚には細かい。入口を別に作り、配線図は奥に置く
