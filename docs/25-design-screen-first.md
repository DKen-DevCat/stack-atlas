# 25. 設計: 画面から始める。コードはエージェントが読む（Phase 10）

作成: 2026-11-11。**状態: 下書き。ユーザーの確認（§7）は済んだ。次は入口のモック。設計レビューは、モックへの反応を反映してから 1 回掛ける。** 要件は docs/24。決定の番号は **D190 から**、質問の番号は **Q34 から**。

この文書も docs/24 §4 の決まりに従い、言語やフレームワークの名前を書かない（今あるコードの部品の名前を指すときを除く）。

## 0. なぜ書くか

- 要件 v2（docs/24）で、Stack Atlas の役割は「本物の画面を見ながら挙動を選ぶと、その経路だけが光り、データが流れる」に絞られた。コードを読むのは利用者の手元のエージェントで、道具は言語に依る処理を持たない
- 今のビューアを、フィクスチャ（71 箱・143 本、画面 3 つ）で見直した（2026-11-11）。配線図の面で名前付きの始点を 1 つ選ぶと、**線のほとんどが光り、経路が 1 本に見えない**。画面は、たくさんある箱の 1 つとして小さく出る。口と項目が全部見えていて、字が細かい。技術者が調べるための図としては正しいが、「直感的にわかる」入口ではない
- 一方で、材料はほとんど揃っている: 箱・口・項目・線の契約（docs/16）、エージェントが箱を書くファイルの形（docs/19 §3）、画面を取りこんで安全に描く仕組み（docs/18 §3.3）、たどる規則と球（`packages/wiring`）、検査（`--strict`）

## 1. 結論

- **入力は 1 つの形にする。** エージェントが、対象の repo の中の `.stack-atlas/` に、箱と線と挙動を書く。今ある「手書きの部分グラフ」（docs/19 §3）を、唯一の入力に格上げする。抽出器・合流・補い（overrides の `v2:`）は無くす（D190）
- **挙動を、名前のある 1 本の経路として持つ。** 今の「名前付きの始点」は、始点からたどれるもの全部を光らせる。挙動は「どの画面の、どの部品を、どうすると」「どの線を順に通って」「何が返り、画面がどう変わるか」を、段の列として書く（D191）
- **ビューアの入口を画面にする。** 本物の画面を大きく出し、その上の部品か、挙動の一覧から 1 つ選ぶ。選んだ挙動の経路だけを、左から右への 1 本の帯で出し、球を流し、段ごとに送るものと返るものを出す。今の配線図は「くわしく見る」先に回す（D192）
- **検査は、言語を知らずにできることだけをする。** 形、参照、根拠（ファイルと行が実在し、名前がそこに書いてあるか）、未読（どの箱にも出てこないファイル）、古さ（根拠の行が、書いたあとで変わったか）（D193）
- **画面の取りこみは「ブラウザで開いたものを保存する」の 1 通りにする。** 部品の位置は、エージェントが書いたセレクタを、ブラウザが測る。対象のコードに印を足させない（D194）

```
今
  コード ─▶ 抽出器 15 個 ─▶ 合流・補い ─▶ graph.json ─▶ ビューア（3D の地図 ｜ 配線図）
            （言語ごと）                                  画面は箱の 1 つ。始点を選ぶと全部光る

これから
  コード ─▶ 利用者の手元のエージェント ─▶ .stack-atlas/（箱・線・挙動・画面の設定）
            （手順書に従って読んで書く）        │
                                               ├─▶ check（形・参照・根拠・未読・古さ）─▶ 直す所の一覧 ─▶ エージェントへ戻る
  動いている画面 ─▶ capture（ブラウザで保存・部品を測る）─┤
                                               └─▶ bundle ─▶ ビューア（画面 → 挙動 → 経路の帯 ─▶ くわしく: 配線図）
```

## 2. 全体像: 誰が何を受け持つか

| 担当 | 受け持つもの | 言語に依るか |
|---|---|---|
| 利用者の手元のエージェント | コードを読む。箱・線・挙動・部品のセレクタを書く。check の指摘を直す | 依る（ここだけ） |
| 人 | 対象のアプリを起動して URL を渡す。挙動の名前と文を直す。エージェントに読ませてよいかを決める | — |
| Stack Atlas | 書く形（契約）、check、capture、bundle、ビューア、手順書 | 依らない |

## 3. 構造

### 3.1 書く形（`.stack-atlas/`）

| ファイル | 中身 | 今あるもの |
|---|---|---|
| `graph/*.yaml` | 箱・口・項目・線。形は docs/16 のまま | 「手書きの部分グラフ」。今は、抽出器の箱へつなぐ線だけ補いの側に書く決まりがある。抽出器が無くなるので、線はすべてここに書く |
| `behaviors.yaml` | 挙動（§3.2） | `views.yaml` と v1 の `flows.yaml` を 1 つにする |
| `screens.yaml` | 画面ごとの URL と、部品のセレクタ（§3.3） | 設定の `screens`・`screenshots` と `regions.yaml` を 1 つにする |
| `DECISIONS.md` | 推定したこと・読まなかった所とその理由 | そのまま |

- 箱には根拠（`file` と `line`）を書く。コードに無い箱（利用者・外のサービスなど）は、根拠が無い理由を `meta` に書く
- 深さはエージェントが決める。**挙動の経路の上は項目まで、それ以外は箱まで**を手順書の目安にする
- 設定ファイル（`stack-atlas.config.yaml`）と補い（`stack-atlas.overrides.yaml`）は無くす。抽出器に何をどこから読むかを伝えるためのものだったので、役目が無くなる

### 3.2 挙動

```yaml
# .stack-atlas/behaviors.yaml（形の例。名前は架空）
- id: post-comment
  name: "コメントを投稿する"
  screen: "screen:/article"            # 画面の箱
  trigger: { part: "part:comment-form", action: submit }   # 画面の部品と、操作
  steps:                                # 通る線を、順に
    - { wire: "part:comment-form#out/body -> handler:create-comment#in/body", say: "入力した本文を送る" }
    - { wire: "handler:create-comment#out/call_1 -> endpoint:POST /comments#in/body", say: "API に渡す" }
    - { wire: "endpoint:POST /comments#req/body -> store:comments#write/row", say: "1 行を書く" }
  result: "一覧を読み直し、コメントが 1 つ増える"
  when: { "screen:/article#logged_in": true }   # 分岐（任意）
```

- `steps` の線は、`graph/` にある線でなければならない（check が確かめる）。挙動は線を作らない。線の上に名前と順番を載せるだけ
- 画面を開いたときの読みこみも、挙動の 1 つとして書く（`action: open`）
- ビューアは `steps` に載った箱・線・項目だけを光らせる。今の「始点からたどる」は、配線図の側の操作として残す

### 3.3 画面の取りこみ

- `stack-atlas capture`: `screens.yaml` の URL をブラウザで開き、描かれた結果の HTML と CSS を保存する。保存したものは、今の消毒（許可リスト。docs/18 §3.3）を通してから置く。同時に、`screens.yaml` のセレクタが指す要素の位置を測って記録する
- 起動と URL は人が用意する。エージェントは URL を足さない・変えない（今の手順書の決まりを引き継ぐ。実サイトや repo の外へ接続させないため）
- 対象のコードに印（今の `data-component`）を足させない。セレクタは、エージェントがコードを読めば書ける
- 特定のビルドの成果物の置き場を読む設定（今の `from: next-export`）は無くす。静的な HTML の置き場を直接指す形だけ残す

### 3.4 check

| 検査 | 何を見るか | 言語を知らずにできる理由 |
|---|---|---|
| 形・参照 | schema、箱・口・項目・線・挙動の段が解けるか | 契約だけを見る |
| 根拠 | `file` が repo にあるか。`line` の近くに、箱の名前（か、箱が申告した文字列）が書いてあるか | 文字列の一致だけを見る |
| 未読 | git が追跡するファイルのうち、どの箱の根拠にも、読んだという申告にも、除外の申告にも出てこないもの | パスだけを見る |
| 古さ | 根拠の行の中身が、書いたときの指紋と変わっていないか | ハッシュだけを見る |
| 挙動 | 段が線に乗っているか。始まりの部品が、取りこんだ画面の中で測れたか | 契約と capture の記録だけを見る |

- 「古さ」が、失った「毎回同じ結果」の代わりになる。図は作り直さず、**check が出した「変わった箱」だけを、エージェントが読み直して直す**
- 今の報告（9-L0）が持つ言語の表は消す。数えるのは、ファイルの数と行数だけにする（docs/24 §3 の条件 3）
- check の出力は、人が読む形と、エージェントが読む JSON の 2 つ（今の `--dry-run --json` を引き継ぐ）

### 3.5 ビューア

```
┌──────────────┬─────────────────────────────────────────────────────┐
│ 画面の一覧     │  本物の画面（大きく）                                   │
│  /            │   ┌───────────────────────────────┐                │
│ ▶/article     │   │  …                 [ Delete ]  │ ← 挙動の始まりの  │
│  /editor      │   │  [ コメント欄          ]        │   部品に枠が出る   │
│              │   │              [ Post Comment ]  │                │
│ 挙動           │   └───────────────────────────────┘                │
│  ページを開く  ├─────────────────────────────────────────────────────┤
│ ▶コメントを投稿│  部品 ──▶ 処理 ──▶ 受け口 ──▶ データの置き場            │
│  コメントを削除│  送るもの: body        返るもの: comment    ●→ 球が流れる │
│  記事を削除    │  結果: 一覧を読み直し、コメントが 1 つ増える  [くわしく見る] │
└──────────────┴─────────────────────────────────────────────────────┘
```

- 画面の上の部品を押しても、挙動の一覧から選んでも、同じ挙動が選ばれる
- 経路の帯は、挙動の `steps` を左から右へ並べたもの。段ごとに、送る項目と返る項目を出す。分岐があれば切り替えを出す
- 「くわしく見る」は、今の配線図を、その挙動の箱と線だけを光らせた状態で開く
- 3D の地図は残すが、入口にしない。手は入れない（§7 の Q35）
- ビューアが `@stack-atlas/core` に依存しない決まり（D44）は続ける

### 3.6 手順書

- 今の skill（`harness/skill/`）を、「抽出器の隙間を補う」から「読んで書く」に書き直す。禁止事項（対象の文に従わない、対象のビルドや通信をしない、秘密を読まない・書かない、書いてよいファイルの許可リスト）はそのまま引き継ぐ
- 読む順番: 画面 → 画面の部品と操作 → その操作が呼ぶ処理 → 受け口 → データの置き場。挙動を 1 本ずつ通す
- 言語ごとの手順や例を書かない。例は、架空の最小の形だけにする
- 特定のエージェントの仕組みに寄せない。本文はふつうの文書で、どのエージェントにも渡せる形にする

### 3.7 消すもの・残すもの

| 扱い | 対象 |
|---|---|
| 消す | `extractors/` のうちコードを読む 13 個、`packages/tf-graph`、core の合流・補い・分類・配置・v1 → v2 の変換、CLI の `build`・`init-flows`・`init-views`、設定と補いのファイルの形、フィクスチャのうち抽出器のためのもの、それらのテスト |
| 残す | `packages/schema`（v2 の契約。v1 は読むだけ）、`packages/wiring`、`packages/viewer`、画面の消毒、`serve`・`diff`・`validate`、メモ、手順書の配布（`init --skill`） |
| 新しく作る | `check`、`capture`、`bundle`（`.stack-atlas/` と取りこんだ画面を、ビューアが読む 1 つの graph.json にまとめる）、挙動の契約、画面から始める入口 |

消すのは、10-1（書きこむ道が 1 本通る）のあと。1 つの PR で消し、消す前にユーザーに確かめる（docs/24 §6）。

## 5. 受け入れ条件

docs/24 §3 の 4 つ。それぞれの確かめ方:

1. 仕事の repo で、画面と挙動を選ぶと、経路が光る — 10-3 で、利用者が手元で確かめる
2. 初めて見る人が、説明なしで追える — 10-0a のモックと 10-3 で、利用者に見てもらう。「何を押すと何が起きるか」を、説明なしで言えるかを聞く
3. 道具のどこにも、特定の言語を前提にした処理が無い — 10-4 のあと、言語とフレームワークの名前の一覧でコード・設定・手順書を検索し、0 件であることをテストにする
4. 準備していない構成の repo でも、道具を変えずにできる — 10-1 と 10-2 を、設計のときに見ていない構成の repo で行う。道具に手を入れたら、条件を満たしていない

## 8. 危ない所

| # | 危ない所 | 手当て |
|---|---|---|
| 1 | エージェントが、無い線を書く・ある線を落とす | 根拠の検査（名前がその行にあるか）、未読の一覧、挙動を 1 本ずつ通す手順。漏れが無いことは保証しない（docs/24 のやらないこと） |
| 2 | 大きい repo で、読む量とトークンが膨らむ | 全部を読ませない。画面と挙動から入り、通った経路だけを項目まで書く。未読は一覧で見える |
| 3 | 図が古くなる | 「古さ」の検査を CI で回し、変わった箱だけを読み直す |
| 4 | 保存した画面に、秘密や個人の情報が写る | 人が用意した確かめ用のデータで開く。消毒は今のものを通す。取りこんだ画面を公開の場所に置かない注意を手順書に書く |
| 5 | セレクタが、画面の作り直しでずれる | capture が「測れなかった部品」を出し、check がエラーにする |
| 6 | 入口の見た目が、作ってみたら直感的でない | 作りこむ前に、モックで確かめる（10-0a） |

## 9. 採らなかった案

- **抽出器を「正確な下書き」として残す**: 言語によって道具の振る舞いが変わる。ユーザーが退けた（2026-11-11）
- **MCP を最初から作る**: 正がファイルにある以上、同じ操作の入口が 2 つになる。要るとわかってから足せる
- **whiteboard の上に全部を載せる**: 本物の画面を載せられず、選んだ挙動だけを光らせる操作が無い（docs/24 §5）
- **今の配線図を磨いて入口にする**: 口と項目を全部見せる図は、どう磨いても最初の 1 枚には細かい。入口を別に作り、配線図は奥に置く
