# 21. 設計: 配線図をまとめて畳む・入れ子に配置する（Phase 8-8、Q19）

作成: 2026-11-10。**状態: 設計だけ（実装前。設計のレビューは実装の前に 1 回）。** Q19 の決定（2026-11-10「ok です、mock なしで行きましょう」= 畳む ＋ 入れ子のレイアウト）を受けた設計。8-7（差分描画: DOM は配置ごとに 1 回作り、選択は class を替えるだけ）が先に入っている前提。決定の番号は D120 から（D114〜D119 は 8-7 に空けてある）。

困っていること: 実リポジトリ（箱 310・枠 6・線 1979）を開くと、配置が 28508×16858 になり、全体を入れる倍率は 0.049（2 面の半分の幅では 0.024）。箱の名前は 0.6px で、全体が見えない。

## 1. 結論

- **畳む単位は「包含の木の切り口」**にする。木は 根 > ディレクトリの段 > group > 箱。開いている入れ物の集合（切り口）が、今見えているものを決める。`@stack-atlas/wiring` の関数は木（親の対応）を引数に取り、`group × runtime` を書き込まない（Phase 9 で木が graph に入ったら、木の作り方だけ差し替える）
- **地図の単位（group × runtime）で畳むだけでは足りない**（実測）。実リポジトリは 310 → 143 箱で倍率 0.19、名前は 2.3px。ディレクトリの段まで畳むと 18 箱・倍率 0.56〜0.70、名前は 9〜11px（畳んだ箱の名前は 16px）になる
- **箱が 100 以下の graph は今のまま**（畳まない。fixture-poly の見た目も既存の e2e も変わらない）。100 を超えたら、開いた直後は「根から 1 段ずつ、見える箱が 24 以下の間だけ開いた」切り口にする
- **畳んだ箱**は、名前の帯と口 1 行（`in/_`・`out/_`）だけの小さい箱。クリックは選択（今の箱と同じ）、開くのは `▸`・ダブルクリック・Enter。**選んでも勝手には開かない**（経路を全部開くと実リポジトリで 310 箱中 260 箱が見えてしまう。実測）
- **線は「見えている端の対」ごとに 1 本**。両端の箱が開いていれば今と同じ項目から項目への線、片方が畳まれていれば畳んだ箱の口へ集まる。開いた入れ物の枠は線を切らない
- **たどる規則と球の時刻は全体の graph のまま**。光るもの・球を「見えているもの」へ写す関数を 1 組にし、3D の地図（今の `litOnMap`・`mapFlow`）と畳んだ配線図の両方がそれを使う
- **入れ子のレイアウト**: 入れ物ごとに中を先に配置し、外の配置からは「大きさとピンの位置が決まった 1 つの箱」として扱う（外は 8-3a のまま）。並びの順は入れ物ごとに 1 回決めて変えない。開閉で変わるのは、その入れ物の大きさと、祖先の中での位置だけ
- **段取りは 3 つの PR**: (a) 木・切り口・写しの関数（wiring だけ）、(b) 畳んだ配線図（配置は今の `layoutWiring` をそのまま通す。ここで実リポジトリの全体が見える）、(c) 入れ子のレイアウト。(c) がいちばん重く、配置の中核に 3 つの追加が要る（§2.6・§9）

## 2. 構造

### 2.1 包含の木と切り口

```
根
├─ <repo>/                    ディレクトリの段（複数 repo では最初の段が repo）
│   ├─ <dir>/…                子が 1 つだけの段はつぶして 1 つにする（`a/b/c`）
│   │   ├─ group              中の箱が 2 つ以上の group（地図のノードと同じ id）
│   │   │   ├─ 箱
│   │   │   └─ 箱
│   │   └─ 箱                 group の無い箱、1 箱だけの group の箱
│   └─ …
└─ 箱                         file の無い箱（利用者など）は根の直下
```

- **木の形（wiring の型）**: `Containment { containers: Map<id, { id, name, kind: 'dir' | 'group', parent? }>, parentOfBox: Map<箱の id, 入れ物の id> }`。JSON にできる・決定的。畳む・写す・配置する関数は、この形だけを見る
- **8-8 での木の作り方** `containmentOf(graph)`: 箱の `file`（group は `groups[].file`、無ければ中の箱の共通のディレクトリ）からディレクトリの段を作り、`group` に箱が 2 つ以上あれば group の入れ物にする。入れ物の id は、ディレクトリが `dir:<パス>`、group は地図のノードと同じ id（メモのキーがそのまま使える）。host の枠は木に入れない（今までどおり枠として描く）。**この関数だけが Phase 9 で捨てるもの**（§7）
- **切り口** = 開いている入れ物の集合 `open`。祖先が全部開いている入れ物・箱が「見えている」。見えていて閉じている入れ物が**畳んだ箱**、見えていて開いている入れ物が**枠**
- **置き場で割る**: 1 つの入れ物の中に、別のレーン・別の host の箱が混ざることがある（実リポジトリで host が混ざる group が 5）。畳んだ箱・枠は「入れ物 ×（host、無ければレーン）」ごとに 1 つ描く。レーンと host の枠の規則（8-3a）を壊さないため。開閉は入れ物ごと（割ったものは一緒に開閉する）
  - 割るので、**同じ名前の畳んだ箱が置き場ごとに並ぶ**。実リポジトリの初めの切り口は、6 つの入れ物が割れて畳んだ箱 17 個（1 つの入れ物から最大 5 個。host の枠の中に 11 個）＋ 箱 1 個。合成 300 箱は、根の直下の 1 つの入れ物が 14 個（host 12 ＋ レーン 2）に割れる。どれがどれかは host の枠とレーンで見分ける（「この Lambda に載っている、このディレクトリのコード」）
  - 割った結果、中が 1 箱だけになっても畳んだ箱のまま描く（規則を 1 つにする。初めの切り口で実リポジトリ 2 個、fixture-poly 4 個）

### 2.2 見える単位と線

- **畳んだ箱の形**: 名前の帯（高さ 26）と口 1 行。左の辺に `in/_`、右の辺に `out/_`（項目が `_` 1 つだけの口は今もある形。fixture-poly では 28 箱が持つ）。幅 200（ふつうの箱は 300）、名前は 16px（ふつうは 12px）で、長ければ切って `<title>` に全部
- **ふつうの箱との見分け**（D31: 凡例・バッジ無し）: 縁を二重にする（重ねた紙の形）。箱の外の左上の「種類」の位置に `フォルダ · 27` / `lib · 5`（入れ物の種類と中の箱の数。D31 の例外の場所をそのまま使う）。名前の帯の左端に `▸`（操作の部品）
- **枠**（開いた入れ物）: host の枠と同じ作り（頭に名前と `▾`、中に子）。入れ子になる
- **線**: 全体の線 w の両端を「見えている端」に写す。端の箱が見えていればその項目、畳まれていれば畳んだ箱の口。**両端の箱が見えている線は今のまま**（線のキーも同じ）。片方でも畳まれていれば、**同じ端の対になった線は 1 本**。両端が同じ畳んだ箱の中に入った線は描かない（球は脈動。§2.3）
  - 開いた箱どうしは、枠をいくつまたいでも今と同じ項目から項目への線（「I/O は常に全部開いておく」「束の線は分かりにくい」への答え: 束になるのは畳んだ所だけ）
  - 2 本以上を束ねた線は少し太くする（2 段階だけ。本数のラベルは出さない）
  - 往復（呼び出しと戻り）は今と同じく 2 本で、隣り合わせて通す（8-3a の束の規則のまま）
  - `foldView` は、見えている単位と線を v2 の graph の形でも返す（畳んだ箱 = 口が `in/_`・`out/_` の箱）。今の `indexGraph`・`layoutWiring` にそのまま通せる（§5 の計測はこの形で行った）
- **切れている線**: 全体の graph で求め、見えている端の対ごとに 1 本（error があれば error）。両端が同じ畳んだ箱の中なら描かない
- **メモ・差分・警告の集約**（どれもバッジを足さない）
  - メモ: group の畳んだ箱は、group か中の箱にメモがあれば右下の角を折る。札は group のキー（地図と同じ）。ディレクトリの入れ物にはメモを書けない（8-8 では。キーが無い）
  - 差分: 中に追加・変更・幽霊が 1 つでもあれば、畳んだ箱を追加の箱と同じ縁の色にする（開くと中身が分かる）
  - 警告（題名の横のリンク。D64）: 一覧から箱を選ぶと、§2.4 の規則で見えている祖先に輪が出る
  - 分岐（variants）: 束の中の線が全部止まっていれば束も止まった線にする

### 2.3 たどる・光らせる・球（地図と共通の写し）

- `select(index, state, selection)` と `schedule` は**全体の graph のまま**。切り口を変えても選択・時刻・周期は変わらない（再生中に開閉しても球の時刻は飛ばない）
- 写しの形を 1 つにする: `Projection { unitOf: 箱 → 見えている単位, lineOf: 線のキー → { line, reverse }（単位の中の線は無い） }`
  - `litOn(projection, lit)` → 光る単位・光る線・始点の単位
  - `flowOn(projection, schedule)` → 線の上の球（同じ線を同じ向きに時間の重なる球は 1 つ。D33）と、単位の脈動（中の線。最短 0.3 秒）
- **地図と配線図で同じ関数**: 今の `litOnMap`・`mapFlow` の中身（対応表で写す・重なりをまとめる・脈動にする）を `litOn`・`flowOn` に出し、`litOnMap`・`mapFlow` は薄い包み（地図だけの規則 = host から光る単位への deploy の束。戻りが束を逆向きに進むことは `lineOf` の `reverse` で表す）として残す。`MapProjection` は `Projection` を満たす。畳んだ配線図は `foldView()` が返す `Projection` を渡す。何も畳んでいなければ、線の球は今の `drawnBalls` と同じ（線ごとに 1 球）
- 箱の中の区間（口から口への対応。今の `drawnBalls` が線の球と一緒に返すもの）は、見えている箱ではそのまま描き、畳まれた箱では描かない（地図の `mapFlow` は今も写していない）
- 8-8 でやるのはここまで。**地図そのものを「同じ木の別の切り口」にする（`projectMap` の v2 → v1 の写し直しをやめる）のは Phase 9**
- 選択の種類は足さない。畳んだ箱・枠の頭のクリックは今の `{ kind: 'group', id, members, label }`（8-6 で地図のノード用に作ったもの。id はメモのキー、members は中の箱）

### 2.4 操作

| 操作 | 結果 |
|---|---|
| 畳んだ箱をクリック | 選択（中の箱ごとにたどって合わせる。地図のノードのクリックと同じ） |
| `▸` をクリック / 畳んだ箱をダブルクリック | その入れ物を開く（選択は変えない） |
| 枠の頭をクリック | その入れ物を選択 |
| 枠の頭の `▾` をクリック / 頭をダブルクリック | 畳む |
| Enter | 選んでいる畳んだ箱を開く。選択の始点が畳んだ箱の中なら、始点までの入れ物だけを開く |
| Shift + Enter | 選択の始点を含む、いちばん内側の開いた入れ物を畳む |
| 題名の横の文字のリンク | `まとめて表示`（初めの切り口）／ `すべて開く`（今の配置） |

- クリックの順は今のまま（型 → 項目 → 線 → 箱 → host → 空白）で、`▸`・`▾` をいちばん先に見る。畳んだ箱の口へ集まる線のクリックは、中身が 1 本ならその線の選択（今と同じ）、2 本以上なら選択にしない（開けば 1 本ずつ選べる）。Esc・`F`・「選択中は hover が効かない」（D31）は変えない
- **選択は切り口を動かさない**。畳まれている箱が選ばれたら（地図のクリック・`?sel=`・`?view=`・警告の一覧から）、見えているいちばん近い祖先の畳んだ箱に始点の輪を出し、そこへ視点を寄せる。中を見たいときは Enter（始点までだけ開く）
- 開閉しても、操作した入れ物の左上は画面の同じ位置に留める（視点を合わせ直す）。動きのアニメーションは付けない
- キーは最後に触った面へ（8-6 の規則）。入力欄にフォーカスがあるときは効かない

### 2.5 最初の状態と URL

- **箱（枠を除く）が 100 以下**: 何も畳まない。配置は今の `layoutWiring(index)` そのもの。**fixture-poly（67 箱）の既定の見た目は変わらず、既存の e2e（8-6 の時点で 58 件）は 1 行も変えない**
- **100 を超える**: 初めの切り口 = 根から 1 段ずつ、「その段の入れ物を全部開いても見える箱が 24 以下」の間だけ開く。実リポジトリは 18 箱、合成 300 箱は 14 箱で始まる
- 木に畳めるものが無い graph（`file` も `group` も無い）は、畳んでも同じなので今の配置のまま
- **URL**: `?open=<id>,<id>…`（開いている入れ物。id は 1 つずつ URL エンコード）。`?open=`（空）は全部畳む、`?open=*` はすべて開く（今の配置）、無ければ上の既定。開閉のたびに `replaceState` で更新する。無くなった id は無視する
- `?sel=`・`?view=` とは独立（選択は切り口を動かさないので、優先の順は要らない。`?view=` が `?sel=` に勝つのは今のまま）
- **localStorage には持たない**（URL が正。再読み込みは URL で戻る。build し直して id が変わったときに古い状態が残らない）。**views にも持たない**（graph.json の契約を変えない。Phase 9 で入れ物の id が決まってから）

### 2.6 入れ子のレイアウト

今の配置は「graph ごとに 1 回だけ決め、選択や分岐で動かさない」（D60）。切り口は、配置を変える最初の状態になる。

1. **中を先に**: 見えている入れ物（× 置き場）ごとに、その子（箱・畳んだ箱・開いた子の枠）だけで 8-3a の配置をする。中は 1 レーン・host 無しなので、レーンの名前や枠は出ない
2. **外からは 1 つの箱**: 開いた入れ物は、外の配置では「幅・高さとピンの位置が決まった箱」。閉じた入れ物は口 1 行の箱。どちらも外の配置（層 → 列 → 順 → 縦の位置 → 配線）は今のまま通る。host の枠は今までどおり外側の塊
3. **枠の縁の通過点**: 枠をまたぐ線は、枠の左の辺（入る）・右の辺（出る）の決まった点を通る。点は「中の見えている端」ごとに 1 つ（同じ項目に入る線は、今も項目のピンで合流している）。外の配置から見ると、枠は「外とつながる中の端」を項目に持つ箱。1 本の線の経路は、外の区間 ＋ 枠の縁から中の端までの区間をつないだ折れ線（深い入れ子では区間が増えるだけ）
4. **順を変えない規則**: 入れ物ごとに、層・列の割り方・列の中の箱の順を**子を全部畳んだ形で 1 回**決めて覚える。開閉で変わるのは子の大きさとピンだけなので、覚えた順のまま、縦の位置（PAVA）・列と通り道の幅・配線だけをやり直す。ほかの箱は、場所を空けるために動くが、上下・左右の順は変わらない（今の配置をただやり直すと順が変わる。実測は §5.2 の E）
5. **計算の範囲**: 開閉 1 回でやり直すのは「開閉した入れ物の中」と「その祖先の縦の位置・配線」だけ。ほかの入れ物の中の配置は覚えたものを使う（中の配置は、その入れ物の下の切り口だけで決まり、外に依らない）
6. **配置の中核（`packages/wiring/src/layout/`）への追加は 3 つ**
   - 大きさとピンの位置を外から与える箱（開いた入れ物）
   - 縁の列（中の配置の左端・右端に、幅 0 の見えない箱を専用の列で置き、縁の通過点から中の端までを今の配線で引く。通過点の縦の順は、中を 1 回配置して中の端の y の順に決める）
   - 順を与えて縦の位置と配線だけをやり直す入口（`arrange` を「順を決める」と「座標を決める」に分ける）

   ほかに、切れている線を外から渡す口が要る（今は `arrange` の中で `brokenEnds` を呼ぶ。畳んだ形では、全体の graph で求めたものを見えている端へ写して渡す）。これは入れ子より前、PR (b) で要る
7. **すべて開く**（`?open=*`）と 100 箱以下の既定は、入れ子ではなく今の平らな配置（枠は host だけ）。実績のある経路をそのまま使う
8. 出力の形は今の `WiringLayout` に `frames`（入れ物の枠）を足したもの。`boxes` には畳んだ箱も入る。`routes` のキーは見えている線のキー（何も畳んでいなければ今の線のキーと同じ）

目標の時間（1440×900、手元の機械）: 開いた直後の配置 50ms 以内（今は実リポジトリで初回 432〜581ms）、開閉 1 回は配置 50ms・描き終わるまで 100ms 以内。

### 2.7 置き場所と計算の時期

- 木・切り口・写し・入れ子の配置は全部 `@stack-atlas/wiring`（純 TS・DOM 無し・決定的）。ビューアは `@stack-atlas/core` に依存しない（D44）
- **build 時に事前計算しない**。木を作るのは 3ms 以下、畳んだ形の配置は 2〜11ms（初めの切り口。実測）。ブラウザで開いたときに計算し、入れ物ごとに覚える（覚えるのは順と、最後の切り口での座標。入れ物の数だけ）
- graph.json・スキーマ・CLI は変えない

### 2.8 ビューアの変更（8-7 との関係）

- 今の `wiring/app.ts` は `layout` を 1 回作って `ScreenLayer`・`Player`・`VariantTable`・`createCanvas`・`selectionFocus` に渡している。開閉で配置が替わるので、これらに「配置を差し替える口」を足す
- 8-7 の分け方（配置ごとに DOM を作る ／ 選択は class を替える）にそのまま乗る: **開閉 = 新しい配置 = DOM を作り直す、選択 = class を替える**。8-8 が 8-7 に求めるのは「DOM を作る関数が配置を引数に取り、何度でも呼べること」だけ。開閉のたびの作り直しは見えている分だけ（初めの切り口で 14〜18 箱）なので、差分での作り直しは 8-8 では入れない
- 光らせる・球は `litOn`・`flowOn` の結果を使う（何も畳んでいなければ今と同じ）
- 画面の箱（iframe）: 畳まれた中にある間は隠す（壊さない。開いたときに読み込み直さない）

### 2.9 3D の地図との関係

- **地図は 8-8 で変えない**（`projectMap` の単位 = group × runtime のまま）。選択の正は配線図（D111）、球の時刻の正は配線図の `Player`（D106）で、どちらも全体の graph の上にあるので、配線図の切り口に関係なく地図は今までどおり光り、球が流れる
- 地図のノードをクリック → 配線図は、その group を含む見えている箱（畳んだ箱か、開いていれば中の箱）が光る。配線図の開閉は地図に何も起こさない
- group の段の畳んだ箱は地図のノードと 1 対 1（host が混ざる group だけ、配線図では host ごとに割れる）。ディレクトリの段の畳んだ箱に当たる地図のノードは無い（中の箱の対応表で写すので困らない）

| 全体を入れたときの倍率 | 1 面で ≥ 0.5（畳んだ箱の名前 16px が 8px 以上）。2 面の半分の幅で ≥ 0.3 |
| 開いた直後の配置 | ≤ 50ms（合成 300 箱・実リポジトリ） |
| 開閉 1 回 | 配置 ≤ 50ms、描き終わるまで ≤ 100ms |
| 開閉での並び | 開閉した入れ物の外にある箱の上下・左右の順の入れ替わり 0（fixture-poly の全部の入れ物で） |
| fixture-poly の既定 | 今と同じ（既存の単体テスト・e2e を変えない） |

**単体テスト（wiring）**

- 木: 基準の graph（poly-86）で入れ物 22（ディレクトリ 16・group 6）・根の子 3、決定的。全部畳むと見える単位 9、上限 24 の切り口で 16。合成 300 箱で 14
- 写し: 全部の線が「見えている線 1 本」か「単位の中」のどちらか 1 つに入る（合計が線の数と合う）。何も畳まない写しで `flowOn` の線の球が `drawnBalls` の線の球と同じ、`litOn` が元の光るものと同じ。`litOnMap`・`mapFlow` の今のテストは変えずに通る（中身を出したことの回帰テスト）
- 切り口を変えても `select`・`schedule` の結果が同じ
- 配置: 決定的、箱が重ならない、子は親の枠の中、線は枠の辺を通過点でだけ横切る、経路は直交でつながっている、開閉しても外の順が変わらない、全部の入れ物を 1 つずつ開閉して落ちない
- 見つかったことの固定: host が混ざる入れ物が host ごとに割れる、1 箱だけの group は入れ物にならない、`file` の無い箱は根の直下、木に畳めるものが無い graph は今の配置と同じ出力

**e2e（fixture-poly を `?open=` で開く。既定は畳まないので）**

- `?open=`（空）: 見える単位 9（畳んだ箱 8・箱 1）。畳んだ箱をクリック → 輪と球（束の上）。`▸` → 枠と子が出て URL が変わる。`▾` → 戻る。Esc で選択だけ解ける
- `?sel=<畳まれた中の箱>&open=`: 祖先の畳んだ箱に輪。Enter → 始点まで開く
- 2 面: 地図のノードをクリック → 配線図の畳んだ箱が光る。再生中に開閉しても再生バーの時刻が飛ばない
- `?open=*` と既定（パラメータ無し）が同じ見た目
- 合成 300 箱（`scale.spec`）: 既定で畳まれて開く（見える箱 14）、開閉 1 回 ≤ 100ms

### 5.3 依頼の前提・前の案と違う結論になった所

1. 「畳む単位 = 地図の単位（group × runtime）」では足りない（B）。docs/18 §3.2 で Q19 の (b) として出していた 1 段の単位（`group` か file のディレクトリ × レーン × host）でも 69 箱・倍率 0.25・名前 3.0px で足りない。**何段もある木を、上から開いていく形**にした。docs/20 §5.1 #1 は地図の単位に `group ?? ディレクトリ` を使わないと決めたが（`route:/` と `layout:/` がまとまり、メモが孤立する）、あれは開けない地図の話で、開ける配線図の入れ物には当たらない
2. 開いた直後に見える 18 箱は、group ではなく**上の方のディレクトリ × 置き場**（6 つの入れ物が 17 個に割れる。§2.1）。group の畳んだ箱は 1〜3 回開いた先にある（27 個のうち 16 個が 1 回）。「group で畳む」と聞いて思い浮かべる絵とは違うので、§6 で確認する
3. 選択で経路を自動で開く案は採らない（D）
4. 「外は 8-3a のまま」は、配置の中核に 3 つ足せば成り立つ（§2.6 の 6）。今のコードは「配置は graph ごとに 1 回」を前提にしていて（`layout/index.ts` の頭の注記、`wiring/app.ts` の `const layout`）、手を入れる所は配置だけでなくビューアの 5 か所にもある（§2.8）
5. 畳んだ箱の名前は、今の 12px のままでは 18 箱でも 6.7px、半分の幅で 3.2px。畳んだ箱だけ 16px にする（D123）。それでも半分の幅で全体を入れると 5.4〜7.2px で、読めるぎりぎり

## 7. Phase 9（モデルを 1 つに）との関係

Phase 9（docs/22 で設計）: graph が包含の木（repo > ディレクトリ > ファイル > 関数の箱 > 口 > 項目）を持ち、3D の地図と配線図は同じ graph の 2 つの切り口になる。`projectMap` の v2 → v1 の写し直しと graph.v1.json は無くなる。

**そのまま使うもの**

- `Containment` の形と、切り口（開いている入れ物の集合）
- `foldView`（切り口 → 見えている単位・線・写し）、`Projection`・`litOn`・`flowOn`
- 入れ子のレイアウト（大きさが決まった箱、縁の列、順を変えない規則、入れ物ごとの記憶）
- ビューアの開閉の操作・`?open=`・配置を差し替える口

**Phase 9 で置き換えるもの**

- `containmentOf(graph)`（今の項目から木を作る関数）→ graph の木を読むだけになる。**8-8 の中で捨てるのが決まっているのはここだけ**（小さい: 関数 1 つとそのテスト）。これが無いと 8-8 は実リポジトリで効かないので、先送りせずに作る
- `projectMap` の単位の規則・id の規則（`group:`・`@runtime`）→ 「group の段の切り口」での `foldView` になる。`litOnMap`・`mapFlow` の包みも要らなくなる
- 入れ物の id（`dir:<パス>`）→ 木のノードの id。8-8 の `?open=` の URL は Phase 9 で開けなくなるかもしれない（無い id は無視するので、既定の切り口で開く）

**木がもう在ったら変えていた所**

- 木を作る関数は書かない。ディレクトリの入れ物にもメモを書ける（id がある）。切り口を views に保存できる
- 「group ≒ ファイル」の読み替えが要らない（ファイルの段がある）
- 置き場で割る規則（× host ?? レーン）は、木が runtime・host を持たない限り Phase 9 でも要る
- 箱そのものも入れ物（口 > 項目）になるので、「箱を口 1 行に畳む」も同じ切り口で書ける。8-8 では作らない（項目だけ閉じても倍率 0.08 で効かない。B）

**先送りを勧めるもの**（作っても Phase 9 でやり直しになる）

- 切り口を views・graph.json に入れること、ディレクトリの入れ物のメモ、地図を切り口から描くこと。どれも 8-8 では作らない
- 入れ子のレイアウト（PR (c)）は捨てにはならないが、いちばん重い。(b) を実リポジトリで見てから着手を決められるように PR を分けてある
- PR (b) の「開いた入れ物の子を、枠なしで平らに並べる」見え方は、(c) で枠に置き換わるつなぎ。配置のコードは足さない（今の `layoutWiring` に通すだけ）ので、捨てる量は小さい

**やらないこと**: 開閉のアニメーション、項目だけを閉じる畳み、host の枠の畳み、build 時の事前計算、graph.json・スキーマ・CLI の変更、切り口の localStorage・views への保存、ディレクトリの入れ物のメモ、地図の変更、面の縦横比に合わせた配置、ELK。

## 9. 危ない所

- **入れ子のレイアウトは測れていない**。§2.6 の 3 つの追加（大きさが決まった箱・縁の列・順を与える入口）は、`place.ts`（846 行）と `columns.ts` に手を入れる。順を覚えても、開いた枠は通る線の本数が変わるので、通過点の束は入れ直しになる。うまく入らなければ「その入れ物の段だけ順を決め直す」（正しいが、順が変わることがある）に落とす
- 開いた枠が 1 つの列を広げる（中が 2604×1625 の枠と、幅 200 の箱が同じ列に入る）。今の「塊だけの列」（host）と同じ扱いにできる見込みだが、確かめていない
- 置き場で割るので、同じ名前の畳んだ箱が host・レーンごとに並ぶ（実リポジトリで 1 つの入れ物から最大 5 個、合成 300 箱は 14 個とも同じ名前）。場所で見分ける設計だが、実物を見て分かりにくければ、名前の付け方を変える
- 目標の時間に余裕が無い所がある: 合成 300 箱で根を 1 段開く（58 箱・線 438）と、平らな配置で 16〜44ms（目標は 50ms）。入れ子にしても中の配置は同じ大きさなので、ここは縮まらない
- 木の段が粗い（次の段を開くと 18 → 53 箱）。上限 24 と 53 の間が無いので、開いた直後の細かさは graph のディレクトリの切り方に左右される
- 半分の幅の面では、畳んでも全体表示の名前は 5〜7px。2 面で全体を読むには、境目を動かすか 1 面（`?pane=wiring`）にする
- 8-7 の実装がまだ手元に無い。「DOM を作る関数を何度でも呼べる」が満たされていなければ、8-8b にその直しが入る
