# 15. 設計: データフローのモデル（箱・口・項目・線）

作成: 2026-11-07。ユーザーとの対話で決めた方向（下記）を、スタックに依存しないモデルとして書く。
`docs/14-design-harness.md` のうち「層を主軸にする」部分（§3.1・§3.2）はこの文書に置き換わる。ハーネス・ビルド成果物の画面・サニタイズ・間隔の計算（§3.3〜§3.7、§4）は引き続き有効で、このモデルの上に載せ直す。

ユーザーの要望（原文に近い形）:

> props 1 つ単位まで見たい。画面を 1 つクリックすると、つながっているノードが全て光り、データが流れ出す。画面の I/O の 1 項目を選ぶと、それのみの流れが分かる。光っている時に線やノードをさらにクリックすると、そこからデータが流れ出す。Go ももっと細かく。Go や TS など、スタックに左右されない作りにしたい。
> 「この型を変えたら、ここが流れなくなる」を即座に理解したい。「今はこうなっているんだ」も知りたい。時間・イベント系も入れたい。
> 選択中は、ほかをクリックしない限り hover で他のノードや線が反応しないこと。選択されているものを最前面にし、背景のラベルが前に出ないこと。セカンダリラベルや冗長な表現を避け、UI 上ではレイアウトで説明すること。

決定: 形式は **C（3D の地図 ＋ 選んだ経路が開く配線図）**。順番は配線図 → 地図。抽出は LSP を使う。

## 1. 結論

- graph は **箱（node）・口（port）・項目（item）・線（wire）** の 4 つで書く。言語・フレームワークの名前はモデルに出てこない。
- 「光る」「流れる」「型を変えたら切れる」は、すべて**項目の単位で線をたどる操作**。フローは人が書くものではなく、たどれば出る。
- キャッシュと時刻・外部イベントも同じ 4 つで書く（キャッシュは口の手前に挟まる箱、時刻は出口しか持たない箱）。
- 言語ごとの違いは「言語アダプタ」（LSP ＋ 1 ページの対応表）と「フレームワーク規約のレシピ」に閉じ込める。モデルと表示は共通。

横軸は **どこで動くか（runtime）** のレーン。縦の層ではなく、左から右に「利用者に近い → データに近い」。これが docs/14 §3.1 の「Z 軸 = 利用者からの距離」の置き換えで、3D の地図（C の地図側）に戻すときは、このレーンを層にすればよい。

## 3. 構造（モデル）

### 3.1 箱（node）

```jsonc
{ "id": "comp:TodayIsland", "name": "TodayIsland", "kind": "component",
  "runtime": "browser",                       // browser | edge | server | data | external | time | user
  "file": "web/src/components/today-island.tsx", "line": 12,
  "ports": [ ... ],                           // 3.2
  "links": [ { "from": "in/date", "to": "out/entries" } ],   // 箱の中で、どの入力がどの出力になるか（3.4）
  "host": "infra:lambda-api",                 // この箱を動かしているインフラ（fn・screen に付く。§8 #6）
  "cache": { ... }                            // kind が cache のとき: policy（ttl・key・scope）
}
```

- `kind` は形と色だけを決める（screen / component / hook / lib / fn / endpoint / table / infra / cache / trigger / actor / external）。層や位置は決めない
- **infra は線上の箱ではなく、箱を包む枠**（`host`）。配線図では fn を囲む枠として描き、線は endpoint → fn に直結する（Lambda を線上に挟むと `event` 1 項目に全部が流れ込んで系譜が粗くなる）。3D の地図では従来どおり箱と `deploy` 辺
- `runtime` が配線図のレーン、地図の層になる。値は固定の語彙（上の 7 つ）で、プロジェクトごとに増やさない
- 粒度の底: TS は **関数・部品**、Go / Rust は **関数**、SQL は **テーブル**。「ファイル」「パッケージ」は箱にしない（折りたたみの単位にはする）

### 3.2 口（port）と項目（item）

```jsonc
"ports": [
  { "id": "in",  "dir": "in",  "items": [
      { "id": "date", "name": "date", "type": "string", "optional": false } ] },
  { "id": "out", "dir": "out", "items": [
      { "id": "entries", "name": "entries", "type": "Entry[]",
        "children": [
          { "id": "id", "name": "id", "type": "string" },
          { "id": "amount", "name": "amount", "type": "number" },
          { "id": "category", "name": "category", "type": "string" } ] },
      { "id": "total", "name": "total", "type": "number" } ] }
]
```

- 口は普通 `in` と `out` の 2 つ。複数あってもよい（Go のハンドラ: `in` = リクエスト、`out` = レスポンス、`err` = エラー）
- **往復する箱**（endpoint・cache など、手前から来て奥へ渡し、奥から戻って手前へ返す箱）は口を 4 つ持つ: `in`（手前から）・`req`（奥へ）・`res`（奥から）・`out`（手前へ）。線は出口 → 入口なので、これが無いと「リクエストが箱を通り抜ける」線が引けない（§8 #1）
- **テーブル**の口は `key`（WHERE・検索条件）・`write`（書くカラム）・`read`（読むカラム）の 3 つ（§8 #8）
- 項目は入れ子にできる（struct の中の struct、配列の要素）。**「props 1 つ単位」はこの項目**
- 項目は `type`（**自分の型**。表示用の文字列。`number`）と `typeRef`（**所属する名前付き型**。`type:Entry`）を持つ。`typeRef` が同じ項目は「同じ型の仲間」として、型をクリックしたときに一緒に光る。テーブルのカラムの `typeRef` は行型（`table:entries`）であって API の型ではない（§8 #5）
- 項目の参照は文字列 `<nodeId>#<portId>/<itemPath>`。例 `comp:TodayIsland#out/entries.amount`（入れ子は `.`）

言語ごとの「何が口で何が項目か」（言語アダプタの対応表。1 ページ）:

| 箱 | in の項目 | out の項目 |
|---|---|---|
| 画面（Next の page） | URL パラメータ、検索クエリ、Cookie | 描画する部品への props、HTML |
| 部品（TS / React） | props の各フィールド、**呼んだ hook・関数の戻り値** | 子部品へ渡す props、**hook・関数へ渡す引数**、コールバックの引数、描画 |
| hook | 引数 | 戻り値の各フィールド |
| 関数（TS / Go / Rust） | 引数の各フィールド（struct は展開）、呼んだ関数の戻り値 | 戻り値の各フィールド、呼ぶ関数へ渡す引数 |
| HTTP の契約（endpoint。往復） | `in`: パス・クエリ・ボディのフィールド、`res`: 実装からのレスポンス | `req`: 実装へ渡すフィールド、`out`: クライアントへのレスポンス |
| テーブル | `key`: WHERE・検索条件、`write`: 書くカラム | `read`: 読むカラム |
| キャッシュ（往復） | `in`: 鍵と（奥から戻った）値 | `out`: 鍵（MISS で奥へ）と値（手前へ） |
| 時刻・外部イベント（trigger） | なし | イベントの属性 |
| 外部サービス（external。Gmail など） | 送る項目 | 返る項目（分かる範囲） |

Rust の例（モデルが言語に寄っていないことの確認）: `async fn today(Query(q): Query<TodayQuery>) -> Json<TodayResponse>` は、箱 `fn:api::today`、`in` = `TodayQuery` のフィールド（`#[serde(rename)]` があれば外向きの名前）、`out` = `TodayResponse` のフィールド。axum の `Router::route("/today", get(today))` が endpoint への線を引く（フレームワーク規約のレシピ）。rust-analyzer が型とフィールドを返す。Go の `net/http` と同じ手順。

### 3.3 線（wire）

```jsonc
{ "from": "hook:useToday#out/entries", "to": "comp:TodayIsland#in/entries",
  "via": "return",           // props | call | return | http | sql | event | render | deliver
  "reply": true,             // 往復の「戻り」側の線（§3.5 の呼び出し元への対応づけに使う）
  "type": "Entry[]",
  "broken": "occurredAt は endpoint の schema に無い"   // 合流点で両側が食い違う線。常に赤の破線（§3.5）
}
```

- 線は **項目から項目へ**。向きはデータが流れる向き（出口 → 入口）
- **線は最も粗い単位で引く**（第 3 版のフィードバック。線の密度の主因だった）: 構造が丸ごと渡るなら親の項目 1 本の線にし、子は親の線に乗って光る（§3.4 の親子の写し）。子の線を別に引くのは、改名（`created_at → createdAt`）や一部の子だけが渡るときに限る。テーブルの読み出しも「行」を親にして 1 本
- `reply` は往復の戻り側。複数から呼ばれる箱の戻りを、光っている呼び出し元へだけ返すために要る（§8 #2）
- `broken` は抽出時の照合で見つけた食い違い（名前・型が合わない）。選択と無関係に常に赤で描く

**型の正規化と「切れる」の判定**（§8 #10 の答え）: 合流点を越えて流れるのは言語の型ではなくシリアライズされた形なので、比較は「線の上の形」で行う。

1. 語彙は OpenAPI と同じ 8 つ: `string` / `integer` / `number` / `boolean` / `datetime` / `bytes` / `object` / `array`。項目はこれを `wireType` として持つ（表示用の `type` とは別。`nullable` も持つ）
2. 言語アダプタが対応表で埋める: TS `number` → `number`、Go `int64` → `integer`、`time.Time` → `datetime`、SQL `bigint` → `integer`、`timestamptz` → `datetime`、Rust `Option<T>` → T ＋ nullable。json タグ・serde rename・`omitempty` も同時に読む。OpenAPI は語彙そのもの
3. 比較は等価ではなく**互換**（包含の表）: `integer` ⊂ `number`、`datetime` ⊂ `string`。送る側が `integer` で受ける側が `number` なら切れない。逆は切れる
4. 切れる条件は 3 つ: 名前が相手に無い（赤）、`wireType` が互換でない（赤）、送る側が nullable で受ける側が必須（黄）
5. 対応表に無い型（branded type・enum・独自スカラ）はアダプタが `unknown` にし、ハーネスのエージェントがレシピか `links` で補う
- 1 つの fetch は 2 本以上の線になる: リクエストの項目（`fetcher#out/path.date → endpoint#in/query.date`）と、レスポンスの項目（`endpoint#out/entries → fetcher#in/response.entries`）
- 箱どうしの関係だけ分かって項目が分からないとき（抽出がそこまで届かない）は、口の単位で引く: `from: "lib:fetcher#out"`。表示は束の線になる。**細かさは段階的に上げられる**
- `via` は線の見た目（HTTP は太い、props は細い、event は点線）と、I/O 境界の判定に使う

### 3.4 箱の中のつながり（links）

項目レベルで流れを追うには、「箱に入った `date` が、出ていく `entries` になる」という箱の中の対応が要る。

- `links: [{ from: "in/date", to: "out/entries" }]`。省略時は **すべての in がすべての out につながる**（箱は不透明）。テーブルだけは既定が `key → read`（WHERE の系譜が読むカラムの上流に全部つくのを防ぐ）
- 型 API のデータフロー解析はここまで出さないので、第一版では **関数の戻り値が引数に依存するか**の簡易判定（引数を参照している戻り値の式）と、分からなければ不透明。ハーネスのエージェントが重要な箱だけ `links` を書き足せる
- キャッシュの箱の links は**状態依存**: MISS は `in/key → out/key`・`in/value → out/value`（通り抜け）、HIT は `in/key → out/value`（折り返し）
- **親子の写し**: 親項目（`entries`）で引かれた線を子（`entries.amount`）からたどるときは、相手側に同名の子があれば相対パスで写し、無ければ段階的に粗くして親へ落とす。`created_at` ↔ `createdAt` のような改名は自動では写らないので、子レベルの `links`（`in/rows.created_at → out/resp.entries.createdAt`）で明示する。言語アダプタが json タグ・serde の rename から埋める

### 3.4b 分岐（variant）

同じ箱でも状態によって経路が変わるものがある: キャッシュの hit / miss、ログイン済み / 未ログイン、クエリ `date` の あり / なし。これを放っておくと、画面を選んだときに複数の経路が同時に流れて読めない（第 5 版のフィードバック: `/today` に入口が 2 つあり、`date` の経路・`open /today` の経路・両方を含む経路の 3 つが重なった）。

- 箱は `variants` を宣言できる: `[{ "id": "hit", "name": "cache hit", "default": false }]`。ログインなら `{ "id": "login", "name": "ログイン済み", "default": true }`、任意のクエリなら `{ "id": "date", "name": "date あり", "default": true }`
- 線・`links`・項目は `when: { "<variantId>": true|false }` で「この状態のときだけ存在する」と書ける。キャッシュの hit / miss の `links` はこれで書く（§3.4 の状態依存の links はこの特殊形）
- **表示は常に 1 つの組み合わせ**。たどるときは `when` が今の状態に合う線・links・項目だけを通る。合わない線・項目は薄く（20%）描いて残し、光らせない
- `when` の変数の持ち主は、既定では「その id を宣言している最も近い箱」（線なら両端、links・項目ならその箱）。箱をまたぐときは `when: { "screen:/today.login": true }` と箱 ID で修飾する。複数キーは AND。OR は線を 2 本に分ける
- UI: 分岐を持つ箱に hover すると、その箱の右上に小さな表が出る。1 行 = 1 分岐、**左の列が「ない」、右の列が「ある」のチェックボックス**（どちらか片方だけ）。切り替えると経路を計算し直して最初から流す。選択中でも hover で表は出る（表は切り替えの入口で、ハイライトではない）
- 抽出: キャッシュは cache 抽出器が、任意の引数・クエリは `optional` な項目から、ログインは認証ガード（`AuthGuard` 系の部品、middleware）のレシピから。分からないものはエージェントが書く

### 3.5 たどる規則（光る・流れる・切れる）

始点 S（箱・口・項目・線のどれか）から:

| 操作 | 始点 | 光るもの | 流れる向き |
|---|---|---|---|
| 箱をクリック | 箱の全項目 | S から線と links を下流にたどった全部 ＋ 上流にたどった全部 | 上流の端から下流へ。S を通る順 |
| 項目をクリック | その 1 項目 | その項目の上流（どこから来たか）と下流（どこへ行くか）だけ | 同上 |
| 光っている線をクリック | その線 | その線から下流だけ | 線の始まりから |
| 光っている箱をクリック | その箱 | その箱から下流だけ（上流は消える） | 箱から |
| 型をクリック（項目の `typeRef`） | 同じ `typeRef` を持つ全項目 | **その型が住んでいる場所**（テーブルの行・struct・OpenAPI の schema・TS の型・props）を全部。流れはたどらない（横断面）。これが「この型を変えたときの最大スコープ」で、次に項目をクリックすると、その中の 1 本に絞り込まれる | なし（静止） |
| 空白をクリック / Esc | なし | 全体（箱と線だけ、項目は畳む） | なし |

「切れる」（赤の破線）は仮定ではなく**コードの事実**にだけ使う: 合流点（endpoint・table・event）で、両側の項目の名前か型が食い違っている線（例: Go は `occurredAt` を返すが OpenAPI の schema に無い）。選択に関係なく常に赤で描く。「型を変えたら影響を受ける範囲」は項目クリックの下流そのもので、別の操作は作らない（2026-11-07 のモックの「型クリック → 下流を赤」は分かりにくかったので廃止）。

**項目の光り方**（塊の光りに加えて、項目の単位でも）: 球が出る瞬間に送り側の項目のピンが強く光り、球が着いた瞬間に受け側の項目のピンが強く光る（0.4 秒で減衰）。親の線で届いた子の項目は、着いたあとに上から順に光る（60ms ずつずらす）。塊（経路全体）の光りは維持し、その上に「いまどの props が入ってきたか」が重なる。

**球（流れるデータ）の規則**: 粒子の列ではなく、**1 通信 = 1 球**。始点の項目から 1 つの球が出て線を進み、箱に入って `links` で分岐する先の数だけ球が分かれる（in の props が 10 なら 10 個の球がそれぞれの props へ入る）。球は線を進み切ってから次の線の球を生む（流れの順序が見える）。往復は行きの球が奥で折り返して戻りの球になる。末端に着いたら少し止まり、全体を最初から繰り返す。

- **呼び出しと戻りの対応**（文脈依存）: 複数から呼ばれる箱の `reply` の線は、光っている呼び出し元へだけ返す。誰も光っていなければ全員へ。上流にたどるときも対称に適用する。実装は **2 段**: まず戻りの絞り込みを無視して範囲を不動点まで求め、次にその範囲を使って戻りの線を絞る（BFS の途中の状態で判定すると順序依存になる。D43）
- **循環**（A が B を呼び、B が A を呼ぶ、再帰）: 範囲は不動点で止まる。球は**同じ線を 1 周回に 2 回流さない**（たどり済みの線を切って DAG にしてから時刻を決める）
- **2 段のたどりの具体形**（8-0a で実装）: 第 0 回は曖昧な戻り（往復の相手が 2 つ以上ある箱の reply の線）を全部切って範囲を出す。第 k 回は「戻り先が前回の範囲にいる、または往復の相手が 1 つも前回の範囲にいない」戻りだけを通す。箱の集合が変わらなくなるまで繰り返す（単調増加なので止まる）。上流へたどるときは対称。線の宣言順を変えても結果が同じことをテストで固定した
- **往復の相手**（requesters）は「X へ reply でない線を引き、かつ X から reply の線を受ける箱」に限る（テーブルへ書くだけの箱は相手に数えない）
- **親に着いた時刻は子にも効く**（8-0b で判明）: 球の時刻を区間の項目の一致だけでつなぐと、親（`getToday#out/call_1`）に着いた対応の先で、子（`call_1.url`）に引かれた HTTP の線が流れない。親から子へ時間 0 の辺を足して最長経路を取る。描く球は線ごとに 1 つ（同じ線を親と子の区間で何度も通るときは最も早い区間。`drawnBalls`）
- **親子の写しで粗くするのは末尾から**（`entries.amount` が写らなければ `entries` へ）。固有の辺（改名の links）を持つ子はその辺だけを使い、親の links は使わない
- 球: クリックした箱の中の所要は 0（最初の球がすぐ出る）
- **親子**: 子が光れば親も光る。親に届いた値は、**固有の辺（links か線）を持つ子へだけ降りる**（キャッシュ HIT の `value` のように子に辺が無ければ子は光らない）
- キャッシュの箱を通る線は、HIT のとき箱で折り返す（`in/key → out/value` だけ光り、その先の上流は光らない）。HIT / MISS の切り替えは表示の状態（既定 MISS）。**光っているキャッシュの箱のクリックは切り替えを優先**し、「下流だけ」はその `out` の項目をクリックする（§8 #7）
- 時刻・外部イベントの箱から始めると、画面を通らないフローになる（Scheduler → Lambda → Go → Gmail）
- 「今はこうなっているのか」は始点なしの全体表示。箱と束の線だけで、項目は出さない

### 3.6 表示の規則（配線図。C の配線図側）

ユーザーの 3 つの要望を規則にする。

1. **選択中は hover が効かない**。クリックで選択している間、ほかの箱・線・項目に hover しても何も変わらない。別の箱・線・項目をクリックするか、空白をクリック / Esc で解くまで固定
2. **選択したものが最前面**。光っている箱・線・項目は常に手前に描く。光っていない箱は暗く沈め（不透明度 15% 程度）、**ラベルを消す**。背景のラベルが手前に出ることはない
3. **説明はレイアウトで**。凡例、バッジ、吹き出しの補足文を置かない。例外は**箱の種類**（`component` / `hook` / `helper` / `screen` / `function` / `endpoint` / `table` / `cache` …）で、箱の**外側の左上**に小さく出す（第 5 版のフィードバック: 名前だけでは何か分からない）。どこで動くかはレーンの位置、何であるかは形と色、流れの向きは線の向きと粒子の動き、I/O の境界は線の太さと形。文字は**箱の名前と項目の名前だけ**。詳しい情報（型・ファイル・キャッシュの policy）は、選んだときに箱の中に開く

レイアウト:

- 横にレーン（runtime）、左から user / time → browser → edge → server → data → external。箱はレーンの中に縦に並ぶ
- 箱は矩形。左辺に `in` の項目、右辺に `out` の項目をピンとして並べる（ノードエディタの形）。**項目は常に全部開いておく**（ユーザーの要望。畳んだ箱と束の線は分かりにくい）。選択は「関係ないものを沈める」だけで、箱の形は変えない。見せる量を減らすのは §3.8 の group の折りたたみで行う
- **無限の平面**（Figma と同じ）: スクロールバーは無く、ドラッグで移動、ホイールとピンチで拡大縮小（カーソル中心）、トラックパッドの 2 本指で移動。初期表示は全体が収まる倍率
- 球の速度は画面上のスライダーで変えられる（0.25〜4 倍）。再生・停止と、最初から最後までの進捗バー（動画の再生バーと同じ。好きな時刻から再生、バーを動かすと流れが追従）を速度の横に置く
- レーンごとに背景をうっすら色分けし、拡大しても自分がどのレーンにいるか分かるようにする

**光りの役割分担**（第 4 版のフィードバック「`/today` を選ぶと光のパターンが 3 つあって分からない」への案。確認待ち）。原因は、シアンを「範囲」と「いま流れている場所」の両方に使っていたことと、球がクリックした所ではなく上流の端から出て、出発点が 2 つ（HTML の配信と `date` の問い合わせ）になっていたこと。

| 役割 | 表現 |
|---|---|
| 範囲（この選択に関係するもの） | **不透明度だけ**。関係するものは通常の色、関係ないものは 12% に沈む。シアンに染めない |
| いま流れている場所 | **球と、球が乗っている線だけ**シアン。着いた項目が白く点滅 |
| 始点 | クリックしたものに白い輪 1 つ |

球は**クリックしたものから出る**（上流の端からではない）。画面をクリックしたら「画面を開いた後に何が起きるか」が 1 本の流れとして下流へ進み、戻りも含めて 1 周する。上流は範囲として見えるだけで動かない。始点が常に 1 つなので、流れは常に 1 本。
- 線は**直交の折れ線**（曲線を使わない。回路図・ELK の直交配線）。束のときは太い 1 本
- **間隔**: 箱と箱の縦の隙間は、そこを通る線の数 × 線間隔（8px）＋ 余白で決める（固定値にしない）。レーンの間の縦の通り道も同じ。箱の中の行間は 18px。配置はプロジェクトごとに違うので手で決めず、層状レイアウト＋ポート制約＋直交配線のエンジン（ELK 相当）に任せる。モックは近似
- **全体表示では線を細く薄く**（1px、不透明度 35%）描き、選択した経路だけを太く明るく描く。全部展開で線が全部見えても、読むのは光っている線だけでよい
- 交差を減らす: 箱の縦順は層状レイアウト（Sugiyama 法の重心ヒューリスティック）で決め、**箱の中の項目は相手側の項目の並びに合わせて並べ替える**（宣言順ではない）。残った交差が「本当にねじれている依存」
- 球は線に沿って流れる（§3.5 の球の規則）。向きは線の向き。キャッシュ HIT は箱で折り返す
- 拡大縮小はマウスホイール、移動はドラッグ。横スクロールと両立する

### 3.7 3D の地図との関係（C の地図側。案。モックを見てから決める）

地図と配線図は**同じ graph の 2 つの見え方**で、違いは「箱をどう並べるか」と「項目を出すか」だけ。

| | 地図（3D） | 配線図（2D） |
|---|---|---|
| 並べ方 | `runtime` を層にして Z に積む（user / time が最上段、data が最下段）。層内は今の自動レイアウト | `runtime` をレーンにして横に並べる |
| 単位 | 箱。項目は出さない。線は口の単位の束 | 選んだ経路の箱だけ。口と項目を開く |
| 画面ノード | ビルド成果物の HTML（docs/14 §3.3） | 同じ HTML を小さく。項目のピンは画面の縁に出す |
| 答える問い | 「今はこうなっているのか」（全体、どこに何があるか） | 「この項目はどこから来てどこへ行くか」「この型を変えたらどこが切れるか」 |

地図から配線図への遷移は 2 案ある。

- **案 1: 浮かび上がる**。地図で箱をクリックすると、その経路の箱だけが層から手前に浮き、他は沈む（今のハイライトと同じ）。もう一度クリック（または「開く」）で、浮いた箱がレーンに整列して配線図になる。カメラは正面に回る。戻ると元の位置に沈む。地図と配線図が**同じ空間**にあり、往復が連続している
- **案 2: 切り替える**。地図でクリックすると画面の右半分に配線図が開き、地図は左に残って選択を映す。地図で別の箱を選ぶと配線図が差し替わる。実装が簡単で、地図の全体像を見失わない

推しは案 1（「Figma に 3D を足した」の体験に近い）。ただし実装量が大きいので、最初は案 2 で作って案 1 に育てる手もある。モックを見たあとに決める。

- 地図側の間隔・圧縮・境界の帯は docs/14 §3.2・§3.6・§4 のまま。キャッシュの箱が境界の帯に対応する（帯 = 層の間に挟まるキャッシュの箱）
- 地図の層は `runtime` の 7 値から**存在するものだけ**を出す（静的エクスポートなら server の層は Go だけになる）。層をプロジェクトごとにエージェントが決める方式（docs/14 §3.1）は取り下げ、`runtime` の語彙に固定する

### 3.8 規模と折りたたみ

実アプリでは箱が数百、項目は数千になる。見せる量を操作で絞る。

- **全体表示**（始点なし）では、箱を **group**（ファイル・パッケージ・feature ディレクトリ）に畳んで出す。group の単位は言語アダプタが `file` から導く既定（TS はディレクトリ、Go はパッケージ）で、ハーネスの設定で変えられる。畳んだ group の線は束 1 本
- **選択**で経路が開くと、経路上の箱だけが group から出てきて、項目を開く。経路外は group のまま沈む
- 項目は **選んだ項目に関係するものだけ**開く（箱をクリックしたときは、その箱の全項目と、線でつながる相手の項目だけ）。関係ない項目は箱の中で畳む（`… 他 12 項目`は出さない。畳んだことはピンの無い辺で分かる）
- 深い入れ子（struct の中の struct）は 1 段だけ開き、クリックで次の段

### 3.9 名前付きの始点（flows.yaml の置き換え。D28）

人が書くフローは廃止するが、「主要な 3 つの流れ」をチームで共有したい要望は残る。そこで**始点と状態**だけを保存する。

```yaml
# .stack-atlas/views.yaml
- id: today-miss
  name: 今日の画面を開く（キャッシュ無し）
  start: screen:/today          # 箱・項目・線のどれか
  caches: { cache:swr: miss, cache:cloudfront: miss }
- id: today-hit
  name: 今日の画面を開く（SWR HIT）
  start: screen:/today
  caches: { cache:swr: hit }
- id: notify
  name: 朝の通知
  start: trigger:scheduler
```

- 表示はこの状態を再現してたどるだけ。経路はコードから出るので、コードが変わっても文がずれない
- `init-flows` は `init-views` になり、始点の候補（画面・trigger）を列挙する

## 4. 抽出（言語アダプタと LSP）

| 段 | 内容 | 言語依存 |
|---|---|---|
| モデル | 上の 4 つと、たどる規則、表示 | なし |
| 言語アダプタ | LSP サーバの起動（tsserver / gopls / rust-analyzer）と、§3.2 の対応表（何が箱・口・項目か）、`links` の簡易判定 | あるが薄い（1 ページ） |
| フレームワーク規約のレシピ | ルート登録（Next の `app/`、`HandleFunc`、axum の `route`）、DB 呼び出し（sqlx・`database/sql` のクエリ文字列 → テーブルとカラム）、イベント（Scheduler のターゲット、SQS）、キャッシュ（SWR・CloudFront behavior） | フレームワークごと。ハーネスのエージェントが書き、`recipes/<framework>.md` に蓄積する |

- **言語アダプタの実装手段は「型 API」で、LSP は補助**（2026-11-07 の検証 §7 で修正）。LSP の標準プロトコル（`documentSymbol` / `hover` / `typeDefinition` / `references` / `callHierarchy`）には**型の構造展開**（プロパティ列挙・配列要素・`Promise` 剥がし・union の非 null 化）、JSX 属性 → 子の props の対応、分割代入名 → props 名の対応、`return` 式の識別子解析が無く、hover の文字列を正規表現で割ることになって脆い。なので TS は compiler API（言語サービス）、Go は `go/packages` ＋ `go/types`、Rust は rust-analyzer（LSP。struct フィールドと fn シグネチャは `documentSymbol` / `hover` で足りる）を使う。「LSP を使う」という決定は「**各言語の型情報を手元のツールで取る。新しい言語は LSP から始められる**」と読み替える
- 取るもの: 関数・部品・struct とフィールド（箱・口・項目）、型と `typeRef`、同じ言語の中の呼び出しと props の受け渡し（線）、`return` 式が参照する引数（`links` の簡易判定）
- I/O の境界（HTTP・SQL・イベント）はコンパイラが型をつないでくれない。**合流点の箱**（endpoint = OpenAPI、table = SQL、event = イベント名）に両側が線を引く形にし、名前・パス・カラム名で照合する。ここは docs/12 の D17 と同じ考え方で、言語に依存しない。**項目レベルの照合は、そのまま「契約と実装のずれ」の検出になる**（§7）
- 今の抽出器（ts-imports・go・openapi・sql・api-link・tf-graph）は、箱と「口の単位の線」を出す**第一版のアダプタ**として使える。項目まで下げるのが型 API の仕事

他の言語を足すとき（ユーザーの問いに答えたもの。2026-11-07）:

| 言語 | 型情報を取る手段 | 項目レベルの精度 | レシピになるもの |
|---|---|---|---|
| Java | Eclipse JDT（jdtls の LSP か JDT 直接）、JavaParser ＋ symbol solver | 高い（静的型、DTO のフィールド、Jackson の注釈が外向きの名前） | Spring の `@GetMapping` → endpoint、JPA の entity → table、`@Scheduled` → trigger |
| PHP | intelephense / phpactor（LSP）、nikic/php-parser | 中。型宣言と docblock がある所は取れる。連想配列で受け渡す所は項目が出ない → エージェント | Laravel の route → endpoint、Eloquent → table、Symfony の属性 |
| Rust | rust-analyzer | 高い（serde の rename が外向きの名前） | axum / actix の route、sqlx |

言語アダプタが「レシピ」（フレームワーク規約）に頼る場所（検証で確定）:

| 場所 | 規約 | 誰が書くか |
|---|---|---|
| HTTP ハンドラの in / out | `r.URL.Query().Get` / `r.PathValue` / `json.Decode(&v)` / `json.Encode(x)`（Go net/http）、axum の `Query<T>` / `Json<T>`、Next の `searchParams` | レシピ（フレームワークごと 1 回） |
| ルート登録 → endpoint | `HandleFunc("GET /today", …)`、`route("/today", get(today))`、`app/**/page.tsx` | レシピ |
| SQL のテーブル・カラム | クエリ文字列の正規表現（テーブル、読むカラム、書くカラム、WHERE） | レシピ |
| SQL のカラム → struct のフィールド | `rows.Scan(&t.ID, …)` の引数順、sqlx の struct タグ | レシピ。無ければエージェントが `links` |
| 外向きの名前 | Go の json タグ、Rust の `#[serde(rename)]` | 言語アダプタ |
| `useState` を通る流れ | setter 呼び出しの追跡（crude） | アダプタの簡易判定。精度が要る箱はエージェントが `links` |
| `map[string]any` / `interface{}` / 生 `fetch` のボディ | 型が無い | リテラルのキーを読む特別扱い。無理ならエージェント |

|---|---|---|
| D27 | graph は箱・口・項目・線で書き、層や位置は `runtime` から導く。kind は形と色だけ | 「props 1 つ単位」「型を変えたらどこが切れるか」は項目の単位でしか答えられない |

| D32 | 状態で経路が変わるもの（キャッシュ hit / miss、ログイン、任意の引数）は `variants` / `when` で書き、表示は常に 1 つの組み合わせ。切り替えは箱に hover して出る表（左「ない」右「ある」） | 入口が複数あると経路が重なって読めない（第 5 版） |
| D33 | 球はクリックしたものから下流へ 1 本。上流は範囲として光るだけ。1 通信 1 球、分岐先の数だけ分かれ、合流は全部着いてから。項目は球の出入りで光る | 流れを目で追えること（第 2〜4 版） |
| D34 | 線は最も粗い単位で引き（同じ名前付き型で子が全部写るなら親 1 本）、間隔は線の数で決め、全体表示は細く薄く、選択した経路だけ太く明るく | 線の密度（第 3・4 版） |
| D35 | 合流点の照合は `wireType`（OpenAPI の語彙に正規化）と名前の互換で行い、食い違いだけを赤で常に描く。「型をクリック」は居場所（最大スコープ）、「項目をクリック」が影響範囲 | 「切れる」を仮定ではなくコードの事実にする（第 1 版の混乱） |

見積り（fixture-poly）: 項目は約 90% 自動（型のある所はほぼ全部。残りは `any` / map リテラル / 生 fetch のボディ）。線は言語内の props 100%・呼び出し引数 約 70% が項目レベルで、残りは口の単位（束）に自動で落ちる。HTTP 合流点は約 85%。SQL はテーブル・カラム単位は自動、カラム → struct フィールドは 0%（Scan のレシピかエージェント）。**links は純関数 約 40% が正確、約 30% が crude（state・ローカル変数経由）、約 30% が不透明（ハンドラ・store）で、ここがエージェントの主な仕事**。

落とし穴: ジェネリクスの `T` が `typeRef` に化ける（除外が要る）／`Pick<>`・mapped type は展開できるが alias 名が消える／JSX の spread は型からは展開できるが実際に渡る項目は不明／Go の `map[string]any`・`interface{}` は項目が出ない（リテラルのキーを読む特別扱いで OpenAPI と一致させた）／json タグ無しは Go 名のまま／`go/types` の stdlib importer を共有しないと `context.Context` が別物になる。
